# 04 — Ассемблерный путь расширения ФОРЭКС до F77: проверяемость и эффективность

**Статус:** проект решения (research/design). Репозиторий `re-forex`, ветка `main`,
дата 19.11.2026. Это документ-результат субагента; он не изменяет `src/`,
эталонов, `tests/` и уже существующих `docs/`.

**Предмет:** как безопасно расширить компилятор ФОРЭКС (ИПМ АН СССР, БЭСМ-6)
правками МАДЛЕН-текстов оверлеев `LO*SYN`, `LO*GEN` и рантайма `FORMAT`,
сохранив проверяемость при неизбежном расхождении символьных таблиц и получив
выигрыш в скорости генерации кода.

---

## 0. Резюме (что предлагается)

1. **Единственный источник истины** — аннотированный `src/*.mad`; пересобираемый
   МАДЛЕН-текст `disasm/*.dtran.madlen` должен быть *производным* артефактом
   (генератор/синхронизатор), а не вторым независимо редактируемым файлом.
2. **Подмена идёт точечно**: новая лексика/синтаксис → `LO*SYN`; новое имя
   оператора и кодогенерация → `LO*GEN`; новый `FT*`-диспетчер → `FORMAT`.
   Корень `FOREX*`, `DATAPR*`, `GIV/PG`, `TAK/PG`, `OCTTDE*` не трогаем.
3. **Побайтовая проверка заменяется на управляемую** (golden + manifest
   разрешённых изменений + сравнение полей КОП + homeomorphic mapping меток
   + функциональная регрессия). Полная байтовая идентичность после правки
   недостижима по причинам `docs/05-roundtrip.md`, но *контролируемость*
   расхождений достижима.
4. **Гибрид**: в ассемблере — только «позвоночник» (2–5 слов на точку входа),
   вся семантика F77 — в новом Fortran-рантайме `F77LIBR`. Это даёт лучший
   runtime при минимальной площади опасного ассемблерного кода.

## 1. Workflow правки .mad → PERSO → тесты

### 1.1 Карта подмены: что именно заменять

| Слой | Каталожное имя в PERSO | Файл-источник тела | Что правим под F77 | Комментарий |
|---|---|---|---|---|
| Корень | `FOREX*` (96 слов, `0o510300..0o510437`) | `build/CORE_ROOT.words` | **не трогаем** | 96 слов без резерва; entry/LINK зафиксированы (S1, `docs/06-address-map.md` §3). Новое внешнее имя = риск сломать загрузку. |
| Синтаксис | `LO*SYN` (1024 слова) | `build/LO_SYN.words`, `src/LO_SYN.mad` | новые ключевые слова (`IMPLICIT`, `SAVE`, `PARAMETER`, `END=`), обработчики в зоне `1517..1777` | оверлей грузится по `0o22654`; 25 внутренних целей — см. §2.3 |
| Генерация | `LO*GEN` (1024 слова) | `build/LO_GEN.words`, `src/LO_GEN.mad` | таблица имён операторов `0532..0623`, кодогенерация внутри 1024 слов | внутренних переходов **нет** (`include/LO_GEN.xref.md` §1) — все адреса абсолютные |
| Рантайм | `FORMAT` (61 слово, `0o510443`) | `build/RUNTIME_FORMAT.words`, `src/FOREX_RUNTIME.mad` | новая пара `UJ FT*nnn / ATX 77xxx` для list-directed I/O | 11 подтверждённых пар из S1:15565-15586 (`docs/06-address-map.md` §3.1) |
| Рантайм | `FORTLIBR` (69 слов) | `build/RUNTIME_FORTLIBR.words` | только если меняется печать/WRITLIBR | трогать в последнюю очередь |
| Вспомогательные | `DATAPR*`, `GIV/PG`, `TAK/PG`, `OCTTDE*` | `*assembler` / байт-точный дамп | **не трогаем** | `OCTTDE*` — псевдоним во избежание конфликта имён с системным `OCTTDEC` (`docs/16-glissade-run.md` §2) |
| **Новый** | `F77LIBR` (новая зона, резерв `0o2305..0o2477`) | Fortran-исходник, собирается патченным ФОРЭКСОМ | вся семантика F77 (см. §4) | добавляется в конец каталога PERSO, **не** в начало (`docs/14-perso-write.md` §1.2) |

**Порядок записи в каталог:** новые записи только в конец, после завершателя
`0 / FULWORD`; вставка в начало сдвигает номера входов личной библиотеки и ломает
`C=0o6700` (`docs/14-perso-write.md` §1.2, п. «Новые записи добавлять ТОЛЬКО…»).

### 1.2 Детальный workflow (8 шагов)

**Шаг 0 — зафиксировать golden.**
```bash
cd /tmp/.private/azizz/opencode/re-forex
sha256sum build/FOREX_PERSO_2300.bin build/LO_SYN.words build/LO_GEN.words \
          build/RUNTIME_FORMAT.words build/CORE_ROOT.words > logs/f77_gold.sha256
cp build/FOREX_PERSO_2300.bin build/FOREX_PERSO_2300.gold.bin
```
Golden-бинарник и golden-дампы неизменяемы; все patched-артефакты идут в
`build/patched/`. Это единственный способ контролировать расхождения при
изменённой нумерации меток (§2).

**Шаг 1 — контрольная пересборка БЕЗ правок (обязательный нулевой прогон).**
Собрать неизменный `disasm/LO_GEN.dtran.madlen` и `LO_SYN.dtran.madlen` через
`*MADLEN` на томе 2348, извлечь объект и сравнить с golden по §2. Цель — измерить
базовый «шум» симтаблицы до внесения семантических правок. Ожидаемый результат:
для `LO*GEN` все 1024 слова cmd-секции совпадают (внутренних меток нет, адреса
абсолютные), для `LO*SYN` — расходятся не более чем в 25 позициях внутренних
целей. Если шум больше — останавливаемся и разбираемся, а не правим F77.

**Шаг 2 — правим источник.**
Правка в `src/LO_GEN.mad` (таблица `0532..0623`) / `src/LO_SYN.mad`
(зона `1517..1777`) / `src/FOREX_RUNTIME.mad` (FORMAT). Сохраняем:
- 6-символьное ограничение МАДЛЕН на имена (`docs/10-naming-conventions.md` §6);
- комментарии МАДЛЕН: `С` в позиции 0 — строка, `.` после пробела — инлайн
  (навык `madlen-build`; точка как целая строка = 33 ошибки);
- линии `С--- слово NNNN … машинное слово …` побайтовой привязки — не удалять,
  они нужны манифесту (§2.4).

Одновременно регенерируется compilable-вариант в `disasm/*.dtran.madlen`
(через генератор, а не руками). Рекомендуемыйgenerator: вырезать `С`-комментарии
и строки дампа, оставить только МАДЛЕН-директивы.

**Шаг 3 — сборка МАДЛЕН-компилятором (*MADLEN на 2348).**
Дека по образцу `tools/build_forex_perso.py::assemble_source()` и
`docs/05-roundtrip.md`:
```
шифр 419999 зс5^
лен 40(2348-wr)^
ееВ1а3
*name
*call yesmemory
*assembler
<disasm/LO_GEN.dtran.madlen |лострочно>
*to perso:402400
*end file
``````
еконец
```
Запуск: `BESM6_PATH=<tmp>:/usr/local/share/besm6 dispak asm.b6`.
Монитор печатает `ДЛИНА LIBRARY <NNN> ЗОН`, `КОНЕЦ ЗАДАЧИ` — это критерий
успешной трансляции (не побайтового совпадения!).

**Шаг 4 — извлечь объект.**
```bash
besmtool dump 2348 --start=1280 --length=3 --to-file=/tmp/newmod.bin  # 0o2400
python3 ~/Yandex.Disk/re-siprod/tools/siprod_lib.py /tmp/newmod.bin
```
`1280` = `0o2400` — **десятичный** аргумент `besmtool`; мониторные карты —
восьмеричные. Из DMS-объекта берём `body = words[s:sec['end']]`,
`L = cmd + const + bss` (по образцу `assemble_source()`), пересчитываем запись каталога
`f1/f2/f3` по формуле `docs/15-perso-build.md` §2.

**Шаг 5 — подменить модуль в PERSO-образе.**
В `tools/build_forex_perso.py` у соответствующего `compiled`-элемента меняем
источник с `build/*.words` на `{body, load}` свежесобранного DMS:
- `LO*SYN` / `LO*GEN` → заменить `body` и `load` (должно остаться `load=1024`);
- `FORMAT` → заменить `body`, `load` (было 61);
- новую `F77LIBR` → добавить в конец списка `modules`.
Пересобрать: `python3 tools/build_forex_perso.py` → новый
`build/FOREX_PERSO_2300.bin` + SHA256. **Имя в каталоге сохраняем прежним**
(иначе не разрешится `FOREX*` → `LO*SYN`/`LO*GEN`, `docs/14` §4.1).

**Шаг 6 — проверка слоя PERSO.**
```bash
tests/install-forex-perso.sh     # 9 модулей, PLCATALOG без ИСПОРЧЕН, зоны 0o2300..0o2304
```
Ожидаемо: `ИСПОРЧЕНЫ ПОДПРОГРАММЫ` отсутствует; границы `0o2277`/`0o2305`
идентичны эталону (скрипт проверяет сам). Если `load` оверлея изменился —
перепроверить f1/f2 (`L` > 511 заходит в младшие биты f2).

**Шаг 7 — функциональные тесты** (§5) + control-by-manifest (§2).

### 1.3 Ловушка `0o22654`: один адрес на два оверлея

`LOADANGO` (экстракод `*21`, `monsys.9:0o774467 … aex 2655(16),*21 22654(12)`)
копирует **1024-словное тело как есть** по адресу `0o22654`; релокации нет
(`docs/06-address-map.md` §1.1). Следствия, которые обязательно соблюдать при правке:

1. Каждый оверлей компилируется как автономный 1024-словный блок с internal-адресами,
   отсчитанными от `0o22654`. Нельзя «слить» SYN и GEN в один модуль: последняя
   загрузка перекроет первую (см. п. 4.2 `docs/14`: последний `*PERSO`/загрузка побеждает).
2. **Любой рост кода должен компенсироваться сжатием внутри тех же 1024 слов.**
   Нет «просто дописать 20 слов в конец» — 1024 слово — жёсткая граница зоны.
   Если не влезает → выносим код в рантайм (§4), либо пересобираем с перераспределением
   таблиц (тогда RJ пересчёт f1/f2 и полная регрессия обязательны).
3. Адреса в оверлеях — уже слинкованные абсолютные (`0o4xxxx/0o5xxxx/0o6xxxx/0o77xxx`,
   LINK `0o74000..74077`). Переименовывать их в символические имена запрещено без
   доказательства «адрес → имя» (`docs/10-naming-conventions.md` §5): `confirmed`
   только `0o74022 → LOADANGO`, `0o74010..13` — контекстно.
4. Тест должен прогонять оверлеи **в последовательности** (синтаксис → генерация),
   как это делает `*forex`; одного «прогнал LO*GEN отдельно» недостаточно.

## 2. Проблема симтаблицы и способ проверки

### 2.1 Природа расхождения (не баг, а свойство символьной сборки)

`docs/05-roundtrip.md` §3: на контрольном ADRSEK (65 слов) после обратной сборки
**все коды операций совпали**, а 27 слов отличались **только полями
операндов/символов** — МАДЛЕН заново нумерует метки, поэтому индексы в симтаблице
другие. Без сохранения исходной симтаблицы побайтовое совпадение невозможно.
`tools/dtran_wrap.py:make_dms()` подтверждает механику: синтетическая симтаблица
заполняется числовыми именами `NNNNNB` и имеет длину `0o7777` (иначе dtran падает
по segmentation fault).

Для оверлеев ситуация **лучше**, чем для ADRSEK: в `LO*GEN` нет внутренних
переходов (`include/LO_GEN.xref.md` §1 — все 504 команды управления идут вовне),
значит операндные поля — готовые абсолютные адреса и при сохранении порядка слов
должны воспроизвестись один-в-один. В `LO*SYN` — 25 внутренних целей
(`docs/06-address-map.md` §1.1, п. 2); вот они и дадут расхождения. Это нужно
проверить нулевым прогоном (шаг 1) **до** внесения правок. Если шум больше —
останавливаемся и разбираемся, а не приступаем к F77-правкам.

### 2.2 Многоуровневая проверка L0..L5

| Уровень | Что делает | Инструмент / артефакт | Критерий |
|---|---|---|---|
| **L0 Golden** | Храним неизменные эталоны + SHA256 | `build/*.gold.bin`, `logs/f77_gold.sha256` | SHA256 совпадают с зафиксированными в `docs/15` §4 |
| **L1 Опкоды** | Пословно сравниваем поле КОП (6 бит) каждой 24-битной половины `[ИР:3][КОП:6][АДР:15]`; поле АДР игнорируется | новый `tools/compare_opcodes.py` (cmp `gold` vs `patched`) | 0 различий вне зон правки; в зонах правки — только ожидаемые |
| **L2 Homeomorphic mapping** | Строим взаимно-однозначное соответствие `метка(old word N) → метка(new word N)` по номерам слов из аннотаций; проверяем сохранение графа переходов (predecessor/successor, call targets) на неизменённой части | `tools/check-label-mapping.py`, расширение `docs/09-crossrefs.md` | bijection на 1024−|patch| словах; каждый internal-target old→new встречается одинаковое число раз |
| **L3 Функциональная регрессия** | 16 сценариев + F77-тесты, сравнение нормализованного вывода с golden | §5, `tests/run-glissade-forex.sh` (14/14 строк) | rc=0, никаких `ERR/ОШИБКА/НЕДОПУСТИМ` |
| **L4 Управляемый diff (manifest)** | Разрешаем изменения **только** в объявленных диапазонах слов; вне их — побайтовое тождество | `tests/check-source-words.py --manifest build/patched/manifest.json` | расхождений вне `allow` = 0 |
| **L5 Воспроизводимость** | Дважды собрать один и тот же `.madlen` на одной версии dispak → одинаковый SHA256 patched-объекта | `cmp` двух сборок | SHA256 совпадают (версия dispak зафиксирована в логе) |

### 2.3 Homeomorphic симтаблица — что именно проверяем

Формат манифеста (новый файл, пример для гипотетической правки):
```json
{
  "module": "LO*GEN",
  "golden": "build/LO_GEN.words",
  "patched": "build/patched/LO_GEN.words",
  "allow": [
    {"words": ["0532", "0623"], "kind": "operator-name-table", "reason": "F77 list-directed"},
    {"words": ["0710", "0740"], "kind": "inline-codegen", "reason": "PRINT * fast path"}
  ],
  "expect_opcode_diff": 6,
  "expect_word_diff": 14
}
```
Инварианты, которые обязан держать `check-source-words.py --manifest`:
1. Для всех `i ∉ allow`: `gold[i] == patch[i]` (побайтово, как сейчас 1024/1024).
2. Для всех `i ∈ allow`: поле КОП либо совпадает, либо явно перечислено в
   `expect_opcode_diff`; каждое изменение ≤ объявленного `expect_word_diff`.
3. Отображение `φ: old_word_index → new_word_index` — сюръективно и
   сохраняет порядок для всех неизменённых слов ( homeomorphism ), т.е. если
   старая метка `Wnnnn` правилась на `Wmmmm`, то все ссылки на `nnnn` заменены
   на `mmmm` согласованно, без «висячих» ссылок.
4. LINK-ячейки и абсолютные адреса (§1.3, п. 3) не изменяются — сравниваются
   как обычные слова вне manifest.

Это заменяет «честное сообщение о расхождениях» из `docs/05` на **контролируемое
расхождение с подтверждённым основанием**.

### 2.4 Что хранить как «золотой» бинарник

- `build/LO_SYN.words`, `build/LO_GEN.words` (уже есть, SHA256 в `src/*.mad` head);
- `build/FOREX_PERSO_2300.bin` (SHA256 `aab191de…a83`, `docs/15` §4) — копия
  `.gold.bin`;
- `build/RUNTIME_FORMAT.words`, `build/RUNTIME_FORTLIBR.words`;
- выводы эталонных дек: `tests/forex-glissade/output.gold.txt`,
  `/home/azizz/Yandex.Disk/dispak/tests/forex/output.txt`, все
  `tests/plan-f77/work/*/out.txt` (моментальный снимок 15 зондов).

## 3. Специфические правки под F77: трудоёмкость и риск

База — наблюдаемый прогон зондов (лог `logs/plan_f77_probes.txt`, 15 сценариев,
системный ФОРЭКС 2.02 на диске 2048). Успешны 10: BASE, DOLOOP, BLOCKIF,
CHARSTAR, DOUBLPR, COMPLEX, DATAST, PARAMETER, INTRINSIC, EXTERNAL, LOGICAL;
**падают 4**: `LISTDIR` (`ОШИБКА В ССЫЛКЕ НА ФОРМАТ`), `IMPLICIT`
(`НЕДОПУСТИМ КЛЮЧ СЛОВО`), `ENDREAD` (`НЕДОПУСТИМ СИМВОЛ * В ВЫРАЖ`),
`SAVE` (`НЕДОПУСТИМ КЛЮЧ СЛОВО`). Именно они — цель правок.

| Правка | Где в исходнике | Слов в образе | Строк в `.mad` | Риск | Почему |
|---|---|---:|---:|---|---|
| Имя оператора в таблице `0o532..0o623` | `src/LO_GEN.mad:503-531`, 29 TEXT-констант через слово (0533, 0535, …, 0623), дескриптор длины в 0532 (`FMT_NAME_LEN`) | **2–5 на имя** | ~2 на имя + правка дескриптора | **ВЫСОКИЙ** | таблица полностью упакована (58 слов `0o532..0o623`), свободного сло́ва нет; рост сдвигает всё после 0623 и требуется пересчёт базы M7/дескриптора |
| Кодогенерация (inline) в `LO*GEN` | основная процедура, слова `23..1777` | **10–40 на конструкцию** | 20–60 | **ВЫСОКИЙ** | все 1024 слова заняты; придётся вытеснять что-то или перераспределять; любая ошибка = неверный объектный код без диагностики |
| Ключевое слово + обработчик в `LO_SYN` | зона `1517..1777` (176 слов), плюс таблицы автомата `Э36 «втбрз»`, разбросанные по телу | **30–90 на оператор** | 40–120 | **ВЫСОКИЙ** | таблично-управляемый конечный автомат; новое состояние надо связать со всеми входами; 176 слов ≈ 2–3 операции максимум |
| `FT*` entry в `FORMAT` | `src/FOREX_RUNTIME.mad`, 11 пар `UJ FT*/ATX 77xxx`, слова `0o510443..0o510522` | **3–6** | 5–15 | **СРЕДНИЙ/НИЗКИЙ** | есть свободные LINK-ячейки `0o74014..0o74077` (заняты `0o74001..13`, `0o74022`); конфликт зависит от модуля — проверить `docs/06` §3.1 |
| Новый Fortran-рантайм `F77LIBR` | отдельный Fortran-исходник, отдельная зона PERSO | 50–150 (новая зона) | 100–300 | **НИЗКИЙ** | не трогает упакованные таблицы; регистрируется в конец каталога; тестируется автономно |

**Итого по минимальному F77-пакету** (list-directed I/O + `IMPLICIT`/`SAVE`/
`END=`): ассемблерная часть ~40–90 слов (LO_GEN 10–25, LO_SYN 30–60, FORMAT 3–6),
Fortran-рантайм ~150–300 слов в новой зоне. Попытка сделать **всё** в ассемблере
требует ~150–250 слов внутри уже заполненных 1024+1024 — практически нереально без
полной перекомпоновки оверлеев.

**Дополнительный риск F77-правок:** формирование сообщений об ошибках. В зонде
CHARSTAR уже наблюдается авария `***FOREX ERROR ADDR 00004 INSTR 1100000700000000`
при неверной ссылке на формат — значит таблица диагностики тоже плотная и
новые коды ошибок надо планировать заранее (выделить диапазон, зафиксировать
в `include/FOREX.labels.md`).

## 4. Эффективность и гибридный путь

### 4.1 Почему ассемблерные правки быстрее в runtime

`LO*GEN` — генератор кода: он **inline** выдаёт команды в объектный модуль
(см. `src/LO_GEN.mad` — ATX/ATA в буфер, сложение указателя, VJM только на
внешние подпрограммы). Для оператора F77 («PRINT *», «END=») ассемблерная правка
даёт 5–15 команд, вставленных непосредственно в тело программы. Альтернатива — вызов
подпрограммы рантайма — это `VJM` (сохранение возврата, настройка M16),
передача аргументов через COMMON/регистры, LINK-ячейка `0o740xx`, загрузка
резидентного модуля. На БЭСМ-6 это ~5–10 лишних команд **на каждый оператор**.
Для транслятора, обрабатывающего десятки тысяч операторов, разница заметна —
именно поэтому исторический ФОРЭКС и сделан как два компактных оверлея с
inline-генерацией.

### 4.2 Почему ассемблерные правки хуже проверяются

- Нет символической семантики: правка — это machine word со смешанными полями;
  «посмотреть, что изменилось» можно только через дизассемблер.
- Абсолютные адреса `0o77xxx`/`0o57xxx` не имеют имён (`docs/06` §7) — ошибка
  в адресе не будет поймана компилятором.
- Симтаблица при пересборке меняется (§2), поэтому стандартная побайтовая сверка
  `tests/check-source-words.py` перестаёт быть применимой «как есть».
- Ошибка в таблично-управляемом автомате `LO*SYN` проявляется не на тесте
  «новый синтаксис», а на случайном старом — нужна полная регрессия (§5).

### 4.3 Рекомендуемый гибрид: минимум ассемблера + Fortran runtime

```
[LO*SYN]  распознать ключевое слово → 1–2 слова таблицы + переход    } позвоночник
[LO*GEN]  имя оператора в 0532..0623 → 2–5 слов + вызов FT*new       } ~10–25 слов
[FORMAT]  FT*new → 1 пара UJ/ATX + LINK-ячейка                       } ~3–6 слов
                              ↓ вызов (одна VJM на конструкцию)
[F77LIBR] Fortran-подпрограммы: list-directed I/O, SAVE, PARAMETER,
          END=, диагностика                                    ~150–300 слов
```

**Обоснование:**
1. Ассемблерная часть — это только *точка входа*; она целиком попадает в
   `manifest.allow` (§2.3) и проверяется opcode-сравнением + homeomorphic mapping.
2. Fortran-часть написана на языке, который этот же ФОРЭКС умеет компилировать;
   она ревьюится как обычный Fortran, имеет собственные unit-тесты и не требует
   дизассемблера.
3. Потеря производительности — **одна VJM на редко используемую F77-конструкцию**
   (IMPLICIT/SAVE/PARAMETER — объявления, вообще один раз на программу;
   list-directed I/O — регулярно, но это и так I/O, где стоимость форматирования
   доминирует). Горячие конструкции (DO-циклы) остаются inline — их не трогаем.
4. Новый модуль `F77LIBR` не требует пересборки 1024-словных оверлеев: это
   отдельная зона PERSO, добавляемая в конец каталога (`docs/14` §1.2).

**Когда отступить от гибрида:** если профилирование покажет, что list-directed
I/O в_hot_-цикле даёт >10% времени — добавить отдельным manifest-патчем inline
fast-path в `LO*GEN`, не смешивая с основной правкой.

### 5.4 Sliding window сравнение с Фортраном-ГДР

Когда доступен эталонный компилятор Фортран-ГДР (GDR/ES ЭВМ), применяется
не побайтовое, а **оконное** сравнение результатов:

```
для каждого сценария s:
  A = normalize(FOREX_patched(s))     # дата, адреса загрузки, мусор монитора
  B = normalize(FORTRAN_GDR(s))
  W = 3                                # окно из 3 строк
  HA = { hash(a[i:i+W]) : i }          # rolling hash по строкам
  HB = { hash(b[j:j+W]) : j }
  score = |HA ∩ HB| / max(|HA|, 1)
  PASS, если score ≥ 0.95 И первая и последняя строки результата совпали
```

Обоснование: Фортран-ГДР и ФОРЭКС могут по-разному форматировать числа и
печатать сервисные строки (FACE/HDR), но **последовательность вычисленных
значений** должна совпадать; скользящее окно из 3 строк устойчиво к вставке/
удалению одной служебной строки и при этом детерминировано (в отличие от
размытого «похоже»). Первая расходящаяся позиция окна пишется в лог — это
и есть диагностический контрольный вектор. Порядок прогона: сначала 16 сценариев
на patched ФОРЭКС (должны пройти сами по себе), затем то же на ГДР, затем окно.
Если ГДР-эталон недоступен в этой среде — уровень помечается `SKIP (нет эталона)`
и не блокирует приёмку; базовый критерий — 16/16 + manifest.
