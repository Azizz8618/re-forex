## 0. Краткий ответ

1. `*FILE` — **стартовая (job-control) карта заказа ресурсов**, а не оператор Fortran.
   Синтаксис (по печатному руководству БЭСМ-6, см. п. 1):
   `*FILE: SCRATCH, <указатель МЛ>, W, <длина>`.
2. Монитор **не создаёт именованный каталог в смысле Fortran OPEN**. Он связывает
   *математический номер устройства (LUN/указатель МЛ)* с **рабочим (SCRATCH) дисковым
   файлом** заданной длины, заполняя системные таблицы `TAPELIST` / `IODCB*` на время
   задачи. Имени файла как самостоятельной сущности в рантайме Fortran нет.
3. Обработка идёт целиком в оверлее `CHEKJOB`: `g02407.f` → `clopen/cldeco` → `G04720`
   → `G05634` + `LUN*MON`, плюс `G04052/G04066` (контроль дублирования LUN).
   `HANDLE` в реконструкции — **пустая заглушка** (`,SJ,`).
4. **Главный вопрос: нет.** Ни один runtime-путь Fortran (IOCONT*, IOXXFMR*, LUNTYP,
   SETIODCB, FT*REGIM) не имеет параметра «имя файла» и не содержит вызова, который
   связывает имя с LUN во время выполнения. Ближайшее — `SETLUN*` (только внутренние
   поля I/O) и `LUNTYP` (только *запрос* типа). Для настоящего OPEN нужен патч
   монитора/рантайма — это совпадает с вердиктом `20-open-close.md` §0, §3.

## 1. Полный синтаксис карты `*FILE`

### 1.1 Авторитетный_peчатный источник

`/home/azizz/Yandex.Disk/besm6-new/besm6.net/book/fortran-1976/01-besm6.md:392-406`
(печатное руководство по Fortran БЭСМ-6, раздел «Заказ рабочего файла на дисках»):

```text
*FILE: SCRATCH, <указатель МЛ>, W, <длина>

Пример:  *FILE: SCRATCH, 41000, W, 40
```

Расшифровка полей (там же, строки 388, 398, 406; и `*TAPE` на строках 382-390):

| Поле | Смысл |
|---|---|
| `SCRATCH` (1-е поле после `:`; в реконструкции — `CARD(2)`) | признак **рабочего файла** (SCRATCH-файла) на диске; вместо имени ленты |
| `<указатель МЛ>` | математический номер направления/устройства: двузначное восьмеричное число, 1-я цифра 3..6 = номер направления, 2-я 0..7 = номер устройства. Допустим также «фортранный» номер `F1..F15`. В примере `41` = ML 41 = фортранный номер 1 |
| `R` / `W` | `R` — только чтение; `W` — чтение **и** запись (RW). Для `*FILE` в примере указано `W` |
| `<длина>` | восьмеричное число **зон по 1 Кбайт** каждая; в примере `40в` зон |

Важно (источник, строка 390): для SCRATCH-файлов **никаких дополнительных процедур
подготовки не требуется** — в отличие от личных файлов на диске. То есть `*FILE`
заказывает *временный* дисковый файл на время задачи.

### 1.2 Что подтверждается исходниками monitor80-re

- **Код карты в таблице**: `chekjob/g02407.f:53-54`
  ```
  *6H*FILE ,
  *01220 1317 2150 0000B,
  ```
  Это 16-й элемент таблицы `k552` (`:23-88`, 69 слов = 23 карты × 3 слова:
  6H-имя + 4-словный кодовый шаблон). Соседи: `*ATAPE/:45-46`, `*FTAPE/:47-48`,
  `*LTAPE/:49-50`, `*DISC/:51-52` («immediate termination», обрабатывается в
  `g02407.f:192-195`), `*TAPE/:57-58`, `*NEW/:59-60`.

- **Декодирование полей**: `chekjob/clopen.asm`
  - `clopen.asm:305-312` — литералы ` READ` и `WRITE`, запись в `CARD(4)`;
  - `clopen.asm:313-324` — проверка `6HSCRATC` (`:314`, константа `:409`), при совпадении
    подставляются внутренние значения `*0362B = :2135 0322 4` и `*0363B = 212`;
  - `clopen.asm:331` — литерал `6H   040` (значение длины по умолчанию);
  - `clopen.asm:333-336` — маски `7776B`/`7775B` и `/S/` при разборе числового поля.

- **Проверки SCRATCH в интерпретаторе**: `g02407.f:198` (`M(2).eq.'scratc'`),
  `:205` (`CARD(2).eq.'scratc'`), `:211` (для `*TAPE`: `CARD(3).eq.'scratc'`).
  Литерал `6HSCRATC` есть и в самом обработчике: `g04720.asm:73,97`.

- **Диапазон LUN**: константы `0..777` (восьм.) приведены в `DFL`-шаблоне
  `chekjob/g02407.f:7-9`: `'*DEFINDIRECT', ':     ', 'LUN   ',
  '/R,RW MODE  /(0.. 777   )'`. В `g04720.asm:32-56` числовое поле обрабатывается
  масками `:7777`, `:1777`, `:0001`, `77 0000`, что соответствует разбору 3-значного
  восьмеричного номера.

> **Оговорка о точности.** В реконструкции `g02407.f` проверка `M(2)` (сырой буфер
> `MONCARD*`) и проверка `CARD(2)` (декодированное поле) дублируются и ведут к одному
> переходу `244`. Почему нужны обе — однозначно из листинга не восстановлено
> (возможно, две формы записи карты: плавающая `:` и фиксированная с пробелом).
> Не спекулирую: фиксирую только факт обеих проверок.

## 2. Семантика: что делает монитор по этой карте

### 2.1 Точка входа и ветка

`chekjob/g02407.f:171-176` — вычисляемый `GOTO` по `CLARG(4)` (код команды, который
класс `clopen/cldeco`). Индекс **15 → `*DISC` (260)**, **16 → `*FILE` (262)**.
Сам код 16 — это позиция `*FILE` в таблице `k552` (`g02407.f:53-54`).

Ветка `*FILE`, `g02407.f:196-208` (дословно):

```fortran
196  C *FILE
197  262  continue
198        if (M(2).eq.'scratc') goto 244
199        if(d03612.ne.0b) goto 271
200        call G04720(CARD, k550)
201        goto 274
202  271  continue
203        call HANDLE(CARD, k550)
204  274  continue
205        if(CARD(2).eq.'scratc')goto 244
206        if(d03611.eq.0b) call G04052
207        call G04066(k550)
208        goto 244
```

Наблюдаемые действия:

1. При `SCRATCH` (любая из двух проверок) **пропускаются** вызовы `G04052/G04066`,
   т.е. не выполняется контроль дублирующегося LUN.
2. В обычном режиме (`D03612 == 0`) вызывается `G04720(CARD, k550)` — реальная
   обработка карты. Если `D03612 != 0` (альтернативный/режим «Дубна»), вызывается
   `HANDLE`, который в реконструкции ничего не делает.
3. `k550` — выходной параметр (номер LUN / код), который затем передаётся в
   `G04066` (`:207`) для диагностики.
4. `G04052/G04066` (`chekjob/g04052.asm:33-76`) ведут список уже выданных
   математических номеров (`*D05453*`, `*D05454*`) и при повторе печатают через
   `LUN*MON` сообщение `ВТОРИЧНЫЙ MAT.HOM.ДЛЯ` (`g04052.asm:134`) и выставляют
   `ERROR = 1` (`:75`). Следовательно, монитор **поддерживает таблицу назначенных
   LUN на время задачи и запрещает дубли**.

### 2.2 G04720 — собственно обработчик карты

`chekjob/g04720.asm:1-101`, DTRAN-модуль от 01.06.84. Объявления:
`MONCARD*:SUBP` (`:2`), `LUN*MON:SUBP` (`:3`), `*FLAGS*:LC` c `D03611,D03612(2),PRIOFL,ERROR` (`:4`),
`G05634:SUBP` (`:5`), `GAL/1 = MONCARD*+8` (`:6`).

Что делает (по командам):

- `:9-17` — сохраняет регистры, **записывает разобранное поле в `D03612+1`**
  (`:12-13`: `10,XTA,1` → `,ATX,D03612+1`) — т.е. фиксирует код режима карты;
- `:18-57` — разбор полей: маски `GOST777777`/`GOST000777`, `6HNZ`, `6H*B`,
  octal `7777`/`1777`/`0001`/`77 0000` — выделение имени, LUN и длины;
- `:58-70` — проверка числа, `*50,112B` (системный extrakod), **`13,VJM,G05634`**
  (`:70`) — вызовelow-level процедуры резервирования/записи в системную таблицу;
- `:71-74` — при ошибке переход на `:78`, где формируется сообщение `6HOШ/СДГ`
  (`:87`) и **`13,VJM,LUN*MON`** (`:82`), затем `,ATX,ERROR`-подобная обработка;
- `:74` — `10,ATX,1` — возврат выходного параметра `k550`.

`G05634` (`chekjob/g05634.asm:1-67`) — низкоуровневая процедура: работает с
абсолютной ячейкой `77 0000` (`:3`), вызывает `*50,156B` (`:6`) — системную
операцию над каталогом/зоной, маски `7777`, `37`, `777` (`:61-64`). Это и есть
«резервирование зоны/связывание номера устройства с файлом».

### 2.3 HANDLE

`chekjob/handle.asm:1-4` **целиком**:

```asm
C Вызывается с параметрами; видимо, для DMS подставляется нечто полезное
 HANDLE:,NAME,
 ,SJ,
 ,END,
```

То есть в этом восстановлении `HANDLE` — **заглушка с немедленным возвратом**.
Ветка `d03612 != 0 → HANDLE` (`g02407.f:199,203`) в Мониторе-80 ничего не делает;
комментарий исходника указывает, что в DMS подставлялась реальная процедура.

### 2.4 Когда связь возникает и исчезает

- **Возникает** — на старте задачи, при чтении карты `*FILE` из потока `MONRED`
  (`g02407.f:160-166`; `MONRED` — entry в `chekjob/chekjob.asm:57-58`, просто
  `,UJ,MONREAD*`). Вызов `G02407` делается из `CHEKJOB*` (`chekjob.asm:33-35`) **до**
  трансляции/загрузки (`chekjob.asm:36-54`: `*50/100`, `G03270`, `CHEKNEWS`,
  `LOADANGO`).
- **Действует** — в течение задачи: номер LUN остаётся приписанным к файлу/устройству
  в таблицах монитора; `LUNTYP` (`src/lib21/LUNTYP.mad:43-53`) возвращает
  тип 2 = SCRATCH-файл для такого номера.
- **Исчезает** — при завершении задачи (освобождение зон монитором). Прямой строки
  в этого репозитория с явным «удалить SCRATCH-файл» нет; печатный источник
  (`01-besm6.md:390`) лишь говорит, что дополнительных процедур prepare/cleanup
  для SCRATCH не требуется. Это единственное обоснование «временности» — дальше
  спекулировать не стану.

### 2.5 Чего `*FILE` НЕ делает

- Не создаёт **именованный** каталогный entry в смысле Fortran `OPEN(FILE='...')`:
  имя поля `SCRATCH` — признак типа, а не имя файла, доступное из программы.
- Не изменяет `IODCB*`: последний заполняется `SETIODCB` (`permanent/setiodcb.asm`)
  из статической таблицы `tabiodcb` — это отображение LUN→устройство, заданное
  при генерации системы.
- Не доступен из программы: `G04720` — DTRAN-модуль оверлея `CHEKJOB`, его нет
  ни в одном `.sym`/`.dtr`/`.masm` (проверено, лог `f77_24_monitor_grep.txt`).

## 4. ГЛАВНЫЙ ВОПРОС: может ли Fortran во время выполнения сделать `*FILE`?

### Ответ: НЕТ. `*FILE` — исключительно стартовый механизм.

#### Доказательство 1 — единственный điểm вызова лежит в стартовом оверлее

- `G02407` вызывается только из `CHEKJOB*` (`chekjob/chekjob.asm:35`), и сразу после
  него идут `*50/100`, `G03270`, `CHEKNEWS`, `LOADANGO` (`chekjob.asm:36-54`) —
  то есть **до загрузки и запуска программы пользователя**.
- Внутри `g02407.f` всё работает с потоком карт: карты читаются `MONRED`
  (`:90,160`) из потока перфокарт; `CLARG(4)` заполняется декодером `cldeco`
  (`clopen.asm:11+`), и только он управляет computed GOTO `:173-176`.
  Ни одна runtime-подпрограмма Fortran не вызывает ни `clopen`, ни `cldeco`,
  ни `G04720`.

#### Доказательство 2 — runtime Fortran I/O оперирует только номером LUN

- `permanent/iocont%.asm:137-170` — entry-точки Fortran-рантайма:
  `FT*002` (`:137`), `FD*642`, `FD*722`, `FC*722`, `FC*642`, `FC*002` (`:142-151`),
  `IOEND*` (`:163`), `FT*003` (`:165`). Ни у одной нет параметра «имя файла».
- `permanent/iocont%.asm:26-33` — блок переменных: `LUN*`, `KLUN = FTXT+6` (`:36`),
  `KSPEC = FTXT+7` (`:39`), `KFORMAT = FTXT+10` (`:38`), `KADDRESS = FTXT+12` (`:37`).
  Это **диагностический шаблон** (`FTXT`, `:709-715`):
  `I/O-ERROR DETECTED IN CALLED FROM LUN '' SPECIFICATION '' FORMAT'12' ADDRESS ''`.
  Есть только LUN/specification/format/address — **нет поля FILE/NAME**.
- `SETLUN*` (`iocont%.asm:373-377`) — ближайшее к «OPEN», но оно лишь переписывает
  внутренние ячейки `22B→113B`, `→107B`; это привязка *внутреннего* номера, а не
  создание файла.
- `permanent/ioxxfmr%.asm:6-31` — низкий уровень READ/WRITE: в аккумуляторе
  «разряды 1-6 — логический номер устройства», разряды 42-47 — END FILE/REWIND/
  BACKSPACE/WRITE/READ/SCHEOF. Опять **только номер**.
- `LUN*MON` вызывается из `iocont%.asm:208,219,307` — но это печать ошибки
  (`lun%mon.asm:1-18`), не изменение таблицы.

#### Доказательство 3 — таблицы устройств заполняются при генерации/старте, а не OPEN-ом

- `permanent/setiodcb.asm:1-45`: `tabiodcb` (`:7-42`) — статическая таблица:
  `5444 0400 7`, `5465 3100 71`, `5547 2500 74`, `5504 3100 72` (`:7-10`) и 16 пар
  вида `4021 3740 4100 0012 / 3777 0000`, `4041 ... 4200 ...`, …, `4401 ... 1600`
  (`:11-42`). Процедура просто копирует 36 слов в `IODCB*` (`:43-44`).
  Вызывается из `MONITOR*` (`permanent/monitor%.asm:85`).
- `permanent/monitor%.asm:83-99` — общее поле: `IODCB*:LC,31` (`:86`),
  `TAPELIST:LC,25` (`:87`), `*REGIM//:LC,1` (`:92`), `MONCARD*:LC,25` (`:94`),
  `IOLIST*:LC,5` (`:97`), `*IOXLCB*:LC,1` (`:98`). Это и есть весь «runtime-каталог».
- `re-forex/src/lib21/LUNTYP.mad:43-53` — `FUNCTION LUNTYP(LUN)`,
  `LUN = 30в..67в`, результат `0=не заказано, 1=лента, 2=SCRATCH, 3=личный файл,
  4=спец. файл`. Тело (`:55-104`) **читает** системную область через `*63 502`
  (`:60`) и `*63 504` (`:66`) — это *запрос*, а не установка.

#### Доказательство 4 — FT_REGIM тоже стартовая карта

`re-forex/src/lib21/FT_REGIM.mad:43-64`:

```text
*CALL FT*REGIM:<LUN>=<LIST>
<LUN> - HOMEP YCTPOЙCTBA: 30-67B ИЛИ F1-F15
<LIST> - CПИCOK CTATYCOB: EC, BUF, KERR, RERR, TEST, STERR
вариант: *CALL FT*REGIM:67=REGIM4
```

Модуль берёт параметры из `*MONCRD*`/`PAR` (`:71`, `MONCRD:LC,BLOCK,PAR`) вызовами
`PARAMT*` (`:96-104`), т.е. **из текста карты монитора**. `PARAMT*` сам явно
описан как «выделение и обработка параметров с текстовых карт»
(`permanent/paramt%.masm:3-12`), буфер `MONCARD/:,LC,14`, работа для управляющих
карт выполняется разделом `STAR*` (`:10-12`). То есть и режим Fortran-обмена —
декларация на старте, а не оператор программы.

#### Доказательство 5 — символьного следа `*FILE` в рантайме нет

`G04720` отсутствует во всех `.sym`/`.dtr`/`.masm` и в `matching/list.txt`;
в `writlib.sym` / `chekjob.sym` есть только `LUN*MON` (печать) и `SETIODCB`.
Значит, Fortran-программа не может даже *вызвать* обработчик `*FILE` по имени.

#### Единственный «почти»-контрпример (и почему он не опровергает ответ)

Редактор DUREAD **синтезирует** управляющие карты во время своей работы:
`duread/g06770.asm:212-232` собирает `*NAME`, `*SFILE`, `*JSPC`;
`:258-275` и `:288-309` собирают `*CFILE`; `duread/g10577.f:58` разбирает
`*SFILE/*WFILE`, `duread/g11133.f:129-132` — `*DFILE/*CFILE`.
Но это **редактор, который вызывает стартовую же систему job-control**, а не
Fortran runtime `OPEN`: никакой Fortran-программе этот путь не доступен, и он не
создаёт связи «имя из FILE= → LUN» для выполняемой программы.

> **Итог для родителя:** совпадает с `20-open-close.md` §0/§3 и `17-lun-p7c.md` §3.
> Настоящий `OPEN` (с `FILE=`, `STATUS=`, `ACCESS=`, `RECL=`) на чистом
> Мониторе-80/ФОРЭКС невозможен; реализуем только unit-state stub
> (`COMMON /J24STT/ OPN(16)`), при этом `FILE/STATUS/ACCESS/RECL` игнорируются.
