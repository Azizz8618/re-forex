`*57 5` — явный **stub под ФОРЭКС** (`e57.cpp:58-61`): автор знал, что ФОРЭКС использует

кода, другой поддиапазон».

READ=0200, NODIAG=0400, BYNAME=01000, ASSIGN=02000, RELEASE=04000`; `ASSIGN` →

(`e57.cpp:106-117`), иначе `disk_find(ACC)` → номер 030..077 (`e57.cpp:119-124`).

### 1.4 Форматы структур (все — `#pragma pack(push,1)`, `extracode.h:27,344`)

**`E57_Search_Info`** (`extracode.h:239-262`) — 4 слова на один запрос:

| Слово | Поля | Комментарий |
|---|---|---|
| 0 | `owner` | имя хозяина, ISO, до 6 символов |
| 1 | `file_name` | имя файла, ISO, до 6 символов |
| 2 | `offset:29, write_mode:1, _1:12, error:6` | бит 30 = режим записи; **сюда пишется ответ** |
| 3 | `disk_unit:6, _2:41, bit48:1` | мат.номер 1:6, бит 48 всегда 1 |

Цикл поиска: `addr += 4`, признак конца — `word[0] == BIT48` (`e57.cpp:174-178`).
`machine.file_search()` возвращает индекс (offset); при нуле выставляется
`E57_NO_ACCESS` (write) или `E57_NOT_FOUND` (read) — `e57.cpp:193-203`; результат
пишется обратно в слово 2 (`e57.cpp:203`).

**`E57_Open_Info`** (`extracode.h:264-275`) — одно слово:

```

write_mode:1
_1:6
disk_unit:6 — куда монтировать (030..067)
error:6    — сюда пишется результат file_mount()
```

Цикл: `addr++`, конец — нулевое слово (`e57.cpp:221-232`).

**`E57_Scratch_Info`** (`extracode.h:225-237`):

```
size:5       — число экстентов, в блоках по 040 зон (т.е. size*040 зон)
_1:31
disk_unit:6  — юнит 030..067
_2:6
```

`machine.scratch_mount(disk_unit, size * 040)` (`e57.cpp:254`). Конец списка — нулевое
слово (`e57.cpp:248-252`).

**Коды ответов** (`extracode.h:280-287`):
`E57_DISK_OFFLINE=010` (бит 43), `E57_DISK_BUSY=020` (бит 44),
`E57_FILE_BUSY=040` (бит 45), `E57_NO_ACCESS=010` (бит 46),
`E57_NOT_FOUND=020` (бит 47), `E57_BAD_REQUEST=040` (бит 48).
(Обратить внимание: 010 и 020 повторяются в разных битах — при порте нельзя
сводить их к одному `errno`.)

### 1.5 Каталог файлов: `Sources / Paths / units`

В Dubna **нет структуры «карта файла» с полями имя/LUN/режим/ёмкость/позиция**.
Есть три разнесённых состояния:

1. **`std::vector<std::string> file_paths`** (`machine.h:73-74`) — единственный
   «каталог»: просто монотонный список путей. Комментарий в коде честен:
   *«This list always increases, never shrinks»* (`machine.cpp:552-554`).
   `file_search()` делает `push_back(path)` и возвращает `size()` — **индекс +1**
   (`machine.cpp:555-559`); `file_mount()` берёт `file_paths[file_index-1]`
   (`machine.cpp:579`). Удаления из каталога нет вообще.

2. **`std::array<std::unique_ptr<Disk>, NDISKS> disks`** (`machine.h:44`, `NDISKS=32`,
   `besm6_arch.h:61`) — соответствие `unit → открытый файл`. Индексы `disk_unit-030`
   (`machine.cpp:572,598`). Дополнительно `mapped_disk` для `*70` phys.io
   (`machine.h:48-49`, `PHYS_IO_UNIT=0100`, `machine.h:139`) — `drum 021 → disk 030`
   в boot-коде (`machine.cpp:936-937,1048-1049`).

3. **Состояние внутри `Disk`** (`disk.h:32-45`): `volume_id`, `path`,
   `write_permit`, `remove_on_close`, `file_descriptor`, `num_zones`, `file_offset`,
   `embedded_data`. Именно здесь живут «ёмкость» (`num_zones`) и «текущая позиция»
   (неявно — через `lseek()` в `disk.cpp:192,226,244,276`), но **позиция не
   сохраняется как логическая переменная F77**: каждое обращение пересчитывает
   абсолютный offset из `(zone, sector)`.

Итог: «карта файла» в Dubna — это **индекс в `file_paths` + юнит в `disks[]` +
(fd, num_zones, file_offset) внутри `Disk`**. Для F77 OPEN/CLOSE её недостаточно:
нужна настоящая запись с именем, статусом, ACCESS/RECL и позицией записи.

### 1.6 Жизненный цикл файла

**Поиск/создание** — `file_search()` (`machine.cpp:492-560`):
- имя диска → каталог: `DISC_LOCAL="."`, `DISC_HOME=$HOME`, `DISC_TMP="/tmp"`
  (`machine.h:134-136`, `machine.cpp:496-510`);
- путь `dir + "/" + word_iso_filename(name) + ".bin"` (`machine.cpp:511`);
- проверка существования via `ifstream` (`machine.cpp:513-519`);
- **write_mode**: пробный `fstream(..., ios::out)`, если файл не существовал —
  удалить (`machine.cpp:521-532`); **read_mode**: `.bin`, затем `.txt`, затем `.utxt`
  (`machine.cpp:533-550`);
- `push_back` → индекс+1 (`machine.cpp:552-559`).

**Монтирование** — `file_mount()` (`machine.cpp:567-608`):
- юнит вне 030..067 → исключение; занят → `E57_DISK_BUSY` (`machine.cpp:569-575`);
- конвертация `.txt→.bin` (COSY) либо `.utxt→.bin` (ISO) — `machine.cpp:585-589`;
- write → создать/обнулить файл (`machine.cpp:591-597`);
- `new Disk(0, memory, path, write_mode, file_offset)` — **`volume_id=0` означает
  «обычный файл», а не SIMH-образ** (`machine.cpp:598`, `disk.cpp:66-78`);
- если `.bin` был временным и режим чтения → `remove_when_finished()`
  (`machine.cpp:599-602`).

**Создание SCRATCH** — `scratch_mount()` (`machine.cpp:613-644`):
- из номера юнита выводится `tape_id = TAPE_SCRATCH | (hi<<4) | lo`
  (`machine.cpp:619-621`, константа `machine.h:127`);
- `mkstemp` по шаблону `scratch<hi><lo>.@XXXXXX` (`machine.cpp:632-633`, `disk.cpp:84-91`);
- `num_zones = size*040`, т.е. до 32×32 = 1024 зон;
- файл физически удаляется сразу после создания, если не `--keep`
  (`machine.cpp:640-643`) — дескриптор остаётся открытым.

**Освобождение** — `disk_release(bitmask)` (`machine.cpp:649-665`): бит
`47 - disk_unit` в аккумуляторе → `disks[unit].reset()`; `file_paths` **не чистится**.

**Запись/чтение** — ТОЛЬКО через `*70` (`extracode.h:35-54`, `machine.cpp:318-351`):
- диск: `offset_nwords = (DISK_ZONE_NWORDS * (zone+4)) + 8 + 256*sector`,
  `DISK_ZONE_NWORDS=8+1024`, `DISK_ZONE_OFFSET=4` (`disk.cpp:182-192,216-226`,
  `besm6_arch.h:50,55`);
- файл: `offset_bytes = (4*zone + sector) * PAGE_NBYTES/4 + file_offset`
  = `(4*zone+sector)*1536 + offset` (`disk.cpp:243,275`);
- слово = 6 байт big-endian (`disk.cpp:248-261,280-290`);
- чтение за концом файла возвращает **нули**, а не ошибку (`disk.cpp:252-254`) —
  прототип «EOF as zero-fill», но без флага.

**COSY/текст** (`cosy.cpp:113-199,297-332`): `.txt` → `.bin` с `*READ OLD`/`*END FILE`
и выравниванием до `PAGE_NBYTES=6144` (`cosy.cpp:144-153`); обратно — `file_cosy_to_txt`
(`cosy.cpp:161-199`), вызывается в `Disk::finish()` (`disk.cpp:128-146`).

## 2. ЧТО МОЖНО ПЕРЕНЕСТИ: алгоритмы и структуры

### 2.1 «可以直接 взять» — спецификации, не код

Это переносится **один-в-один** (сохранение битовых полей критично):

1. `E57_Request_Info` / `E57_Search_Info` / `E57_Open_Info` / `E57_Scratch_Info`
   (`extracode.h:192-275`) — разряды, ключ `06470724040000000`, маску
   `07777774074000000`, 4-словный шаг поиска, признаки BIT48/нулевое слово.
2. Таблицу из 8 операций и **коды ошибок** (`extracode.h:209-218,280-287`).
3. Алгоритм `file_search`: проверка существования + пробная запись + `-1` индекс
   (`machine.cpp:492-560`).
4. Алгоритм `file_mount`: `E57_DISK_BUSY`, конвертация txt/utxt, `remove_when_finished`
   (`machine.cpp:567-608`).
5. Алгоритм SCRATCH: `mkstemp`, `size*040` зон, удаление после открытия
   (`machine.cpp:613-644`).
6. Адресную математику `*70` для файлов: `(4*zone+sector)*1536 + file_offset`
   (`disk.cpp:243,275`) и 6-байтовое слово.
7. Синтаксис карт `*FILE:NAME,LUN[,W][,size]` и `*DISC:1/local`
   (`tests/expect_file_scratch.txt:26-27`, `session_test.cpp:823-838,852-864`).
8. Идею **gated multiplexing**: высокое информационное слово `077777` как селектор
   файловой подфункции при сохранении низких слов под ENTIER — ровно та архитектура,
   которая уже работает в Dubna (`e57.cpp:37-65`).
9. Трассировочные форматы `print_e57_*` (`trace.cpp:610-701`) — как эталон диагностики.
10. lowering `OPEN/CLOSE/INQUIRE → CALL FOPEN/FCLOSE/FINQ` из
    `docs/plan-f77-full/20-open-close.md:35-73` (уже нашей волны A, 0 слов в оверлеях).

### 2.2 「переписать под другую ОС」 — код НЕ переносится дословно

1. **Весь C++ → C/MADLEN.** `e57.cpp`/`machine.cpp`/`disk.cpp` написаны под
   C++-модель Dubna (`std::unique_ptr`, `std::fstream`, `Memory&`). В dispak другая
   модель: `ddisk_t { void *diskh; ushort offset; ushort diskno; ushort mode; }`,
   64 записи, `disks[030..067]` (`17-lun-p7c.md:39,49`). Перенос — только
   *алгоритмический*, не компиляция.
2. **SIMH-формат томов.** `disk.cpp:179-233` читает 8 служебных слов + смещение 4 зоны;
   у dispak свой `disk_readi`/`disk_writei` и свой формат. Брать нельзя.
3. **COSY-конверсию** (`cosy.cpp:113-332`): у Дубны KOI7/COSY, у dispak — DUBNA TEXT
   и свои таблицы (`20-open-close.md:182-183`; `docs/19-dtran-text-encodings.md`).
   Нужна переработка таблиц, не копирование.
4. **`file_paths` как `vector<string>`** → вместо него в Monitor‑80 нужен
   `COMMON /FILMAP/` с явными полями: `NAME(6)`, `LUN`, `MODE(R/W)`, `SIZE`,
   `OPENED`, `RECPOS`, `EOF`, `IOSTAT` (прототип `COMMON /J24STT/ OPN(16)` из
   `20-open-close.md:71-76` — слишком беден, расширяется).
5. **`*FILE`-парсер.** В Dubna его нет в эмуляторе; в Monitor‑80 он есть —
   `g02407.f:53-54,196-208` (`*FILE` → `G04720`/`HANDLE`/`G04066`). Надо дополнить
   разбор полей `W` и `size` и связать с `/FILMAP/`.
6. **Уровень B (таблица допустимости LUN ФОРЭКС).** В Dubna его нет; в Monitor‑80
   он блокирует всё: `НЕТ КАНАLA LUN 45` (`17-lun-p7c.md:37-45,130-140`,
   `23-luntyp-p7c.md:76-95`). Патч LUNTYP бесполезен (`23-luntyp-p7c.md:5-9,93-95`).
7. **EOF/IOSTAT.** В Dubna «EOF» = нули при чтении за концом (`disk.cpp:252-254`) и
   `*READ OLD` в COSY; в dispak признак EOF есть на уровне `Э60` (`reg[016]=0`), но
   теряется в `monread%` (`19-eof-iostat.md:19-27`). Переносить нечего — писать заново.

## 4. КЛЮЧЕВОЙ ВОПРОС: КОНФЛИКТ ЭКСТРАКОДА 057

### 4.1 Это тот же код

**Да, это тот же самый экстракод 057 — но с разными подфункциями.**

- В ДИСПАК/ФОРЭКС: `Э057:0000` = **«entier 2»** (Тюрин-1985, с. 264;
  `re-dispak/docs/tyurin1985/extract-codes.json`, ключ `Э057:0000`, `confidence: confident`).
  Класс по ИР 057 A: «ВЫДЕЛЕНИЕ ЦЕЛОЙ ЧАСТИ (ENTIER) / СИСТЕМНАЯ ОПЕРАЦИЯ»
  (`re-forex/docs/lib21/04-extract-codes.md:161,176-177,228-231`).
- В Dubna: `e57.cpp:39-41` — `addr=0 → besm6_floor(ACC)`, тот же ENTIER.
- **Но** в ДИСПАК 057 — это *многокодовая системная операция*: inform word
  `6`, `1263`, `1247`, `4000`, `4144`, `5`, `-CN1` (`src/FOREX_CORE.mad:198-200,363,368,583`,
  `src/lib21/FOREX_.mad:58,83`, `BEMSH_.mad:201`, `LINK#IPM.mad:244`,
  `TEMP##.mad:45`, `FT_REGIM.mad:172`). В `FOREX_CORE.mad:200` прямо написано:
  *«*57,6 — экстракод 57 (ACCESS), подпрограмма OCTTDE»* — то есть ENTIER — лишь
  одна из подфункций, а не весь код.
- Dubna тоже мультиплексирует: `0=ENTIER`, `2=Calcomp`, `5=Forex-stub`, `77777=файлы`,
  `010+=ленты` (`e57.cpp:37-71`). Совпадение подфункции **5** с ФОРЭКС gw — прямое
  свидетельство, что коды *пересекаются*, но не идентичны.

### 4.2 Фактический конфликт в dispak

`dispak/dispak/cu.c:796-798`:

```c
case 057:
        err = elfun(EF_ENTIER);          /* reg[016] НЕ проверяется */
        goto errchk;
```

Следовательно, `*57 77777` в Monitor‑80 будет **молча посчитано как ENTIER** —
самый плохой исход (не exception, а тихая ошибка). Поиск показал, что
`*57 77777` в `re-forex/src/`, `docs/`, `logs/` **не встречается вообще**
(`logs/f77_24_port_extract_conflict.txt`), поэтому верхний диапазон свободен.

Дополнительно: `Э50 07` в dispak тоже `EF_ENTIER` (`extra.c:1503-1504`) — дублирование
ENTIER в 050 и 057 есть уже сейчас, так что «ENTIER через 057» не уникален.

### 4.3 Рекомендация: какой код/механизм использовать

**Вариант A (рекомендуемый): оставить 057 и добавить гейт по информационному слову.**

```
disp/dispak/cu.c, case 057:
    if (reg[016] == 077777)  err = e57_file();      /* порт Dubna */
    else                     err = elfun(EF_ENTIER); /* все существующие ФОРЭКС-вызовы */
```

Почему это безопасно и дешевле всего:
1. сохраняются **все** существующие `*57` (5, 6, 1263, 1247, 4000, -CN1 и др.);
2. `077777` не используется ни одной программой re-forex (проверено grep);
3. ровно та же схема уже работает в Dubna (высокий селектор + низкий ENTIER);
4. правка — ~10 строк C в `cu.c` + бэкенд `e57_file()` (~150–250 строк C, порт
   `machine.cpp:492-644` и `disk.cpp:53-146`).

**Вариант B (если нужен отдельный Supervisor-код, независимый от ENTIER): Э073 (073B).**

Обоснование по проверенным источникам:

| Код | В `cu.c` dispak | В Tyurin JSON | В MADLEN re-forex | Вердикт |
|---|---|---|---|---|
| 057 | ENTIER (безусловно) | `Э057:0000` = entier 2 | 11 применений | **занят**, использовать только с гейтом |
| 066 | `E_UNIMP` | нет записи | **8 применений** (`LO_SYN` 4513/4502/4515/6151/4546…, `04-extract-codes.md:164,196-198,292-294`) | опасно |
| **073** | **не в dispatch → `E_UNIMP`** | `Э073:77777` — «прекращение обмена по виртуальному номеру устройства», `confidence: low`, с.290 | **0 применений** | **лучший свободный кандидат** |
| 074 | `syscal`/`eexit` (`cu.c:843-858`) | нет | — | занят |
| 076 | `E_UNIMP` как opcode; `e50 076` = TERM OUTPUT (`extra.c:1521-1523`) | `Э076:0210`, связь с М-6000, с.63 | 0 | семантически зарезервирован |
| 077 | записьrecognized конца ленты (`cu.c:868-875`) | нет | 0 | занят |

Э073 идеально ложится на роль «управление файловыми ресурсами»: по Тюрину это уже
`77777`-подфункция, связанная с виртуальными номерами устройств, и в dispak она
не реализована. Можно даже сохранить **тот же формат запроса** `Э073 77777`, что и
у Dubna `Э57 77777`, — тогда бэкенд переносится без переделки битовых полей.

**Вариант C (самый дешёвый, 0 новых экстракодов): вообще не трогать супервизор.**

Собрать всё на PERSO `0o2320`: `FOPEN/FCLOSE/FINQ/FREAD/FWRITE` + `COMMON /FILMAP/`,
обмен через уже работающие `Э70` и `Э50 0131`, поиск — через расширенный `*FILE`
в `g02407.f`. Это ровно то, что уже доказано в `20-open-close.md:92-195` и
`17-lun-p7c.md:79-101`. Минус: остаётся Level B (`НЕТ КАНАЛА`) и нет настоящих
имён файлов — это **профиль**, не полная F77-семантика.

**Итог по вопросу:** коды не «разные» — это один 057. Dubna **переиспользовала старшее
информационное слово 077777** под файлы, сохранив ENTIER в нулевом. В Monitor‑80 надо
либо повторить этот гейт (вариант A), либо, если нужен отдельный код, взять **Э073**
(свободен и в dispak, и в коде ФОРЭКС); **нельзя** просто выдавать `*57 77777` — dispak
посчитает его как ENTIER.

# 7. МОНИТОРНЫЙ ПУТЬ БЕЗ DISPAK (ОПЕРАТИВНЫЙ ВЕРДИКТ)

## 7.0 Почему §4.3 A/B больше не рассматриваются

Запрет на правки dispak снимает оба ранее предложенных приёма: гейт `reg[016]==077777` в
`cu.c:796` и новый экстракод 073 тоже требуют изменения C-хоста. Оставляем **только**
уровень Monitor‑80: исходники `monitor80-re/**`, `src/lib21/*.mad` (только чтение) и
пересборку рабочей копии системного диска **2348**. dispak по-прежнему используется
**как инструмент** — ассемблер/эмулятор в `asm.pl`, `overlay.pl`, `besmtool` — но его
исходники не трогаются. Это важно: «мониторный путь» не означает «без dispak вообще»,
он означает **без правки dispak**.

Одновременно ужесточается честность verdictа: по волнам A3/A (`22-errlun-supervisor.md:151-167`,
`26-file-runtime.md:0,138-209`) простая патч-таблица Level B **не даёт** `WRITE(41)` —
нужна правка кода инициализации/оверлея монитора и пересборка 2348. Ниже — план именно
такой пересборки.

## 7.1 Какие механизмы Dubna реализуются мониторными средствами (без новых экстракодов)

Разрешённые (уже реализованные в dispak) экстракоды: `Э50 0131/0157/0156/0112`
(attach/поиск канала/каталог/смещение тома — `extra.c:1310-1361,1555-1559,1614-1636`;
`g04720.asm:72`, `g05634.asm:6`), `Э63` (АРФА/тип устройства — `LUNTYP.mad:60-90`),
`Э67` (печать), `Э70` (обмен — `cu.c:822-834`), `Э60` (ввод карт, EOF → `reg[016]=0`,
`19-eof-iostat.md:19-27`), `Э64` (печать), `Э74` (STOP).

## 7.3 Вызов из Fortran: `CALL FOPEN(...)` → entry постоянной библиотеки монитора

**Вопрос:** может ли Fortran-линкер разрешить entry из постоянной библиотеки монитора,
без PERSO и без правки dispak?

**Ответ: да, при условии, что новая подпрограмма заведена в каталог постоянной библиотеки
и пересобрана системная зона 2348.** Доказательства:

1. `monitor80-re/matching/list.txt` — это список имён постоянной библиотеки; в нём есть
   `CLOPEN` (`:36`), `GIVLIBR*` (`:91`), `IOCONT*` (`:107`), `LUN*MON` (`:145-146`),
   `MONREAD*` (`:150`), `SETFTN` (`:194`). То есть Fortran-подпрограммы и сервисы монитора
   сосуществуют в одном каталоге имён.
2. `chekjob/chekjob.sym:9,18,70` фиксирует адреса `SETIODCB`, `LUN*MON`, `G04066`;
   `writlib/writlib.sym:4-9` и `inputcal/inputcal.sym:8` дают те же имена (`LOADANGO`,
   `PRINT8`, `LUN*MON`) — единое символьное пространство библиотек.
3. Механизм разрешения: `GIVCALL*` читает карту через `MONREAD*`, проверяет имя через
   `IDENT6` и грузит модуль через `LOADANGO` (`permanent/givcall%.asm:26-43`);
   `GIVLIBR*` читает таблицы `LTABLE*`/`STABLE*` (`permanent/givlibr%.asm:4-9,34-43`);
   `LOADF` экспортирует `LOADT`, `GO`, `DELETE` как `,ENTRY,` (`loadf.asm:41,87,100`).
   Аналогично `CLDECO:ENTRY` (`clopen.asm:11`) и entry `FT*002/IOEND*/FT*003`
   (`iocont%.asm:137,163,165`) — это и есть Fortran-вызываемые точки.
4. Пример из наших дек: `*CALL WORKS*` (subroutine в PERSO) работает
   (`01-f77-standard-matrix.md:171`, `04-verification.md:141`), значит синтаксис `*CALL`
   проходит через dispak и попадает в монитор; разница лишь в том, что цель — не PERSO,
   а постоянная библиотека.

**Рецепт для `FOPEN`:** написать `permanent/fopen.asm` с `FOPEN:,NAME,` + `,ENTRY,`
и соглашением аргументов ФОРЭКС (как `LOADT:` в `loadf.asm:41-59`), внести имя в
каталог библиотеки (`LTABLE*`/`STABLE*` — `ltable%.asm` и `star%.masm`, где уже
объявлены `LUN*MON`, `GIVLIBR*`, `MONREAD*`: `star%.masm:21-33`), собрать через
`asm.pl` + `linker.pl` и записать в свободную зону 2348. Никаких PERSO-зон `0o2310/0o2320`
и никаких C-правок.

**Оговорка:** добавление нового имени в каталог постоянной библиотеки — изменение
системной зоны, поэтому обязательны `snapshot`/`verify` из `21-diskpatch-toolchain.md`
и регрессия `GATE 20/20`. Ограничение в 12 модулей относится к PERSO `0o2310`
(`10-implementation-libr.md:161`), не к постоянной библиотеке.

## 7.6 Честные оговорки

1. Карта `*FILE` в деке dispak **не пропускается** (`26-file-runtime.md:142-150`,
   `28-dispak-passport-files.md:98-100`); её мониторная логика должна вызываться через
   `*CALL …` или фиксированный LUN 41 в инициализации. Это не требует правки dispak — это
   обход на уровне мониторного стартового оверлея.
2. `LUNTYP` в этом пути не участник: `WRITE(41)` его не вызывает (`23-luntyp-p7c.md:78-95`);
   патч `LUNTYP` бесполезен.
3. Патч трёх копий таблицы LUN без правки инициализации и кода `ERRLUN` не работает
   (`22-errlun-supervisor.md:137-143`, `26-file-runtime.md:122-127`).
4. Никакие эталоны, `src/`, `tests/`, исходники dispak не изменяются; все прогоны — на
   копиях 2348 в `/var/tmp`, с обязательным `snapshot`/`verify` и `GATE 20/20`.
