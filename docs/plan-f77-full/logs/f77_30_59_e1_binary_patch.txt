## 1. Карта диска 2048 (ФАКТ, полезно для продолжения)

Формат образа: `zone_t = 8*uint64 cwords + 1024*uint64 data = 8256` байт/зона.
`disk_readi2()` (disk.c) читает логическую зону `Z` по файловому смещению `(Z + ZONE_OFFSET=4) * 8256 + 64`,
слово `k` — по `+ k*8`, 6 байт слова лежат **в обратном порядке** (little-endian uint64 → big-endian word).
`besmtool dump --start=0250` тоже трактует `0250` как восьмеричное (strtol base 0).

Эксперимент `zmap.py` (уникальный маркер в слово `0o770` каждой зоны 0..0o1777, core dump на PC 0o455)
дал точную карту загружаемых при старте зон:

| логич. зона 2048 | RAM page | смещение файла слова 0o770 |
|:--|:--|:--|
| 0o200 | 0o50000 | 0x... |
| 0o201 | 0o46000 | 0x... |
| 0o207 | 0o64000 | код монитора (PC 0o64425 = word 0o425) |
| 0o217 | 0o32000 | |
| 0o227 | 0o34000 (перекрывается 0o36000 на ранней стадии) | **0x139388 = VJM-элемент** |
| 0o230 | 0o30000 | |
| 0o234 | 0o42000 | |
| 0o251 | 0o36000 | |

**Код монитораrewriteable через диск**: слово `RAM 0o64421..0o64427` побайтово равно
`2048 zone 0o207 word 0o421..0o427` (проверено: core `003036f00000` == reverse(file `0000f0363000`)).
То есть патч кода монитора через образ 2048 принципиально возможен.

Подмена 2048 → 2348 работает: 2348 содержит те же служебные слова, в том числе
`0x139388` = `dc8002090000`, монитор стартует нормально.

## 2. Вторая проблема: «наши слова в RAM 0o1770» — НЕ решена (BLOCKER)

### ФАКТ 1: тайминг

`MTR 00455L` — **первое** выполнение VJM в boot-последовательности, до чтения deck и до `*TRANS`.
core dump на PC `0o455` (как в базе, так и с патчем):
```
RAM 0o1770..0o2002 = 00 00 00 00 00 00   (все нули)
```
Слова из зоны `0o1745` диска 2148 загружаются загрузчиком `0o701..0o711` **позже** — при обработке
`*TRANS:OURMRK*,,411744`, то есть **после** первого перехода. Поэтому патч загрузчика
(как и pre-compensation слов зоны `0o1745`) не может подставить слова к моменту первого `vjm 1770`.
C3 решал это C-хуком **в момент STORE по 0o455**, который и происходит непосредственно перед переходом
(лог: 10480 повторов STORE 0o455). В E1 такой хук запрещён.

### ФАКТ 2: попытка trampoline-патча кода монитора

Пробовался чистый бинарный патч кода (файл `tramp.py`, `tramp34.py`, `trampjump2.py`):
- в `2048 zone 0o207 word 0o424` (RAM `0o64424`) вместо `atx` (обнуление 0o455) ставился `uj` на trampoline;
- trampoline в нулевой области `2048 zone 0o201` (RAM `0o46140`) должен был скопировать 11 наших слов
  из `zone 0o201 word 0o100..0o114` в RAM `0o1770..` через modification-регистры
  (`vtm 0o46100(1)/vtm 0o1770(2)`, `xta 0(1)`, `atx 0(2)`, `utm 1(1)`, `utm 1(2)`), затем `uj 0o64425`;
- кодирование инструкций проверено против реальных слов монитора (`b6enc.py`: `uj 702` → `0c01c2` совпало).

Результат: при любом варианте trampoline'а (даже тривиального `uj 0o64425` без копирования)
монитор падает с `КОНТРОЛЬ КОМАНДЫ` на самой первой инструкции по `0o46140`:
```
 КОНТРОЛЬ КОМАНДЫ
 46140: 00 30 64425  uj
 acc=... R=000111
```
То есть переход в область `0o46000` как в код при исполнении монитора не проходит
(вероятная причина: convolution-биты слов зоны 0o201 помечают их как данные, либо защита адреса
при выборке команды; точно не установлено). Патч слова `0o64424` сам по себе рабочий:
без него VJM-патч даёт корректный `vjm 1770(15)` (см. §1в).

### ГИПОТЕЗА (не проверена)

Можно было бы продолжить: записать trampoline в зону `0o207` (код монитора, корректные convolution-биты)
в её нулевом хвосте `word 0o1770..0o1777` (RAM `0o65770..0o65777`, 8 слов), но для 11 слов + цикла
этого места недостаточно; требуется либо уплотнение цикла, либо поиск другого участка кода с
корректными битами. Это и есть точное место, где в C3 потребовался C-хук.

### Дополнительный ФАКТ (важно для оценки «успеха»)

На **stock** dispak (и на `dispak-base`) с нашим телом на диске 2148 консоль **уже**
печатает `OUR-CODE-RAN-7391` даже без всякого VJM-патча (`runs/e1_base/out.txt`, строка 28),
потому что резидентный компилятор монитора сам печатает GOST-/apk words тела при разборе `*TRANS`.
Поэтому один только console-маркер **не является** доказательством исполнения нашего к через `0o1770`:
нужны именно `MTR 00455L vjm 1770(15)` + CORE DIFF слов по `0o1770`, чего в E1 не достигнуто.

## ГИПОТЕЗЫ

* (**подтверждена**) VJM-слово собирается рантаймом из единственного элемента диска 2048
  `0x139388` (зона 0o227, слово 0o621); его патч даёт `vjm 1770(15)` на непатченном dispak.
* (**подтверждена**) 2348 можно подменить вместо 2048 — элемент находится по тому же смещению.
* (**опровергнута для E1**) патч загрузчика `0o701..0o711` или pre-compensation тела `0o1745`
  не решают задачу из-за тайминга: первый VJM исполняется до `*TRANS`.
* (**не подтверждена**) trampoline в коде монитора: переход в page 0o46000 даёт `КОНТРОЛЬ КОМАНДЫ`.

End **BLOCKED**. Точное место, где потребовался C-хук C3: момент `STORE` по RAM `0o455`
(PC `0o64425`, word из буфера `0o53402/0o53403`), где нужно одновременно подставить 11 наших слов
в RAM `0o1770..0o1782`. Чистый бинарный патч(uint8) диска этот момент до сих пор не перехватывает.
