### 1.1. Декодирование управляющих слов MONSYS (ГИПОТЕЗА → подтверждено трассой)

`union E70_Info` из `dubna/extracode.h:30-95`: tract = биты 0..4, sector = 6..7,
unit = 12..17, paragraph = 24..25, page = 30..34, raw_sect = 35, phys_io = 38,
read_op = 39, sect_io = 47. Примеры из `MonsysBootstrapper.cs:47-55`:

```
4014000000210201 -> unit=021, phys=1, read=1, sect=1, tract=1, sector=2  (инициатор монитора)
0014000000210007 -> unit=021, phys=1, read=1, tract=7                    (каталоги)
0014000000210010 -> unit=021, phys=1, read=1, tract=10                   (библиотеки)
4014250300210101 -> unit=021, phys=1, read=1, page=25, sect=1            (статический загрузчик -> 53400)
4014370000210301 -> unit=021, phys=1, read=1, page=37, sect=1            (динамический загрузчик -> 76000)
```

В dubna `e70()` (`extracode.cpp:127-190`) при `phys_io=1` и `unit >= mapped_drum(021)`
перенаправляет обмен на диск 030: `zone = tract + (unit-021)*040`, затем
`disk_io()` добавляет `DISK_ZONE_OFFSET=4`.

## 2. Конвертер (DONE)

Файл: `/var/tmp/b1-f77-fix/413-monsys-simh/scripts/convert_dense_to_simh.py`.

Алгоритм:
1. Читаем `monsys.9` как 294 912 слов по 6 байт big-endian.
2. Создаём образ на 1000 зон × 1032 слова × 8 байт = 8 256 000 байт.
3. Для зоны i (0..287) пишем физическую зону i+4:
   - 8 служебных слов берём из `mons9.d9` (заголовок зоны с номером, магией
     `01370707` и контрольной суммой, тег 2);
   - 1024 слова данных кодируем как `struct.pack('<Q', (1<<48) | word)`.

Команда:

```sh
python3 /var/tmp/b1-f77-fix/413-monsys-simh/scripts/convert_dense_to_simh.py \
  --dense /var/tmp/b1-f77-fix/413-monsys-simh/input/monsys.9 \
  --out   /var/tmp/b1-f77-fix/413-monsys-simh/work/monsys2209.img \
  --headers /var/tmp/b1-f77-fix/413-monsys-simh/input/mons9.d9
```

Результат: `wrote ... 8256000 bytes, 1000 zones, 288 tape zones at physical zones 4..291`.

**Проверка 1 (побайтовая):** все 288 зон данных (`+64` байт от начала зоны,

**Проверка 3 (чтение слова через SIMH):** с патченным копийным бинарником

### 3.1. Формат `.b6` для SIMH (ФАКТЫ, `besm6_sys.c:565-634,792-850`)

- `b <oct>` — адрес (а не `v`; `v` отвергается);
- `k <mnemonic>, <mnemonic>` — инструкция (тег 1);
- `c <16 oct digits>` — данные (тег 2);
- `p <oct>` — PC;
- `get_alnum()` (`besm6_sys.c:285-294`) **не принимает `*`**, поэтому MADLEN-ное
  `*70` надо писать как БЭМШ-ное `э70` (иначе `Invalid input line` + `Format error`).

Готовый файл: `work/monsys_boot.b6`. Проверка загрузки:

## 4. Попытка загрузки в симховском BESM-6

`work/boot_monsys.ini`: md0 = конвертированный образ, drums 0/1 = нулевые
образы по 2 113 536 байт, prn0 = файл, `attach tty1 console`, `load ...`, `g`.

### 4.1. С оригинальным `BIN/besm6` — БЛОКИРОВКА

```
--- (100570) instruction parity error
--- (100500) instruction parity error   (далее миллионы повторов)
```

Причина (ФАКТ): `*70` в SIMH — экстракод, который передаёт управление по
вектору `0500+070 = 0570` (`besm6_cpu.c:1499-1537`), а ячейки 0500..0577 при
старте нулевые (тег 0) → `mmu_fetch()` (`besm6_mmu.c:691`) вызывает
`STOP_INSN_CHECK`. В dubna `*70` обрабатывается хост-кодом
`Processor::e70()` и guest-вектор не нужен. В SIMH нет ни нативного e70, ни
`map_drum_to_disk()` (поиск по `BESM6/*.c` дал 0 совпадений).

### 4.2. С патчем на КОПИИ SIMH — частичный успех

Патч: `work/besm6_cpu.monsys.patch` (113 строк), применяется к копии
`besm6_cpu.c`; добавляет нативный e70 по образцу `dubna/extracode.cpp:127-190`
и возврат из экстракода. Сборка (все остальные файлы берутся из оригинального
SIMH, только `besm6_cpu.c` из копии):

```sh
gcc -std=gnu99 -O2 -I /home/azizz/Yandex.Disk/simh \
    -I /home/azizz/Yandex.Disk/simh/BESM6 -I .../simh_src \
    -D_GNU_SOURCE -DUSE_INT64 -DUSE_READER_THREAD -DSIM_ASYNCH_IO \
    -DHAVE_SEMAPHORE -DHAVE_SYS_IOCTL -DHAVE_LINUX_CDROM \
    -DSIM_HAVE_DLOPEN=so -DHAVE_UTIME -DHAVE_GLOB -DHAVE_SHM_OPEN \
    .../simh_src/besm6_cpu.c <остальные besm6_*.c и sim_*.c> \
    -o work/besm6_monsys -lm -lrt -lpthread -ldl
```

Результат (`logs/console.txt`): загрузка прошла значительно дальше — прочитаны
инициатор, каталоги, библиотеки, /MONTRAN, статический загрузчик в 53400,
динамический загрузчик в 76000:

```
e70 io read file zone 1 sector 2 -> mem 00000 (256 words)
e70 io read file zone 7 sector 0 -> mem 00000 (1024 words)
e70 io read file zone 10 sector 0 -> mem 00000 (1024 words)
e70 io read file zone 36 sector 0 -> mem 76000 (1024 words)
```

После этого процессор уходит в цикл (~97% CPU), но **баннера MONSYS и
приглашения нет**, команды `*NAME WHATIS` / `*CALL WHATIS`, посланные в tty1,
не обрабатываются; `prn0` пуст.

## 5. Почему не удалась полная загрузка (БЛОКИРОВКА — точная причина)

1. Нативный e70 в нашей копии — упрощённый: он **пропускает все WRITE**
   (например `cw=0000000000200000`, `cw=0000000000210000` — записи на барабаны
   при инициализации), грубо сводит барабаны 020.. к md0 и не эмулирует
   статус/GRP/прерывания КМД/МБ. Для честного порта нужен полный
   `dubna/extracode.cpp:127-190` + `dubna/machine.cpp:disk_io()` с
   `DISK_ZONE_OFFSET` и корректными `disk_ctl()`/`drum()` SIMH.
2. SIMH имеет только 2 барабана (`besm6_drum.c:66-68`), а MONSYS работает с
   барабаном 021 через физический обмен; отображения drum→disk в SIMH нет.
3. Экстракоды MONSYS (`e57/e64/e70/e75`) в SIMH также идут через пустые
   вектора 0550..0577; один e70 недостаточен для прикладной задачи.

Это **не** проблема конвертера: конвертер побайтово совпадает с эталонным
`mons9.d9`, а чтение с диска через SIMH подтверждено логами (§2).
