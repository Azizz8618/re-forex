## 3. ФАКТ: бинарный патч монитора 2048 работает (цель 3, часть 1)

Патч элемента, найденного E1: файл `2048`, смещение `0x139388`, 6 байт слова в обратном
порядке; логическая зона `0o227`, слово `0o621`.

```
БЫЛО (file): 00 00 09 02 80 dc   -> 6710000202200000  vjm 64002(15)
СТАЛО(file): 00 00 09 f8 83 dc   -> 6710177002200000  vjm 65770(15)
```

М/TR на НЕпатченном dispak (`runs/final_direct/em.txt`):

```
MTR 00455L vjm    65770(15) AU=5557565164576217 ... 15=00401 16=00061
```

Эмпирическая формула кодирования цели подтверждена: поле адреса = `(цель + 0o14000) & 0o77777`.
Вариант E1 (`02 80 -> f8 9b`) даёт `vjm 1770(15)`; наш (`f8 83`) даёт `vjm 65770(15)`.

Трамполин записан в **логическую зону 0o207** диска 2048 (физическая зона файла `0o213`),
слова `0o1770..0o1777` → `RAM 0o65770..0o65777`. Это зона КОДА монитора, слова исполняются
(проверено MTR; в отличие от зоны 0o201, где E1 получал «КОНТРОЛЬ КОМАНДЫ»).

**ФАКТ (исполнение наших слов, `runs/cond6e`):**

```
MTR 65770L xta    1770(0)     <- наша команда загрузки
MTR 65770R uza    65772(0)    <- наш условный переход
MTR 65772L uj     64002(0)    <- возврат в резидентный старт при первом VJM
MTR 64002L wtc    43(0)
```

То есть наш бинарный патч монитора **реально перехватывает VJM и исполняет наши слова**
в зоне кода. (Код opcode `uj` = первая структура `0o110`; `uza` = `0o106` — сверено с
реальными словами монитора по MTR.)

## 4. ГИПОТЕЗЫ и негативные результаты (цели 3, часть 2; 4)

1. **ГИПОТЕЗА «наши слова в ОЗУ к моменту первого VJM» ОПРОВЕРГНУТА для чистого бинарного патча.**
   Первый `VJM 0o455` исполняется в boot-последовательности до чтения деки; в ядре на этом
   PC `RAM 0o1770..` = нули. Тело из зоны 1551 (и из 0o1351) в ОЗУ не грузится:
   `runs/cat_body_core_final` — CORE DIFF = 0 совпадений.
2. **ГИПОТЕЗА «условный трамполин по содержимому RAM 0o1770» ОПРОВЕРГНУТА.**
   На втором `VJM 0o455` (в базовом прогоне он есть: `reg15=01030`, `reg01=02034`) ОЗУ
   `0o1770..` также нули — загрузка кода компилятора происходит **после** этого перехода.
3. **ФАКТ:** после подмены цели VJM на наш трамполин во всех прогонах наблюдается
   **только ОДНО** исполнение `0o455` (даже при `BESM6_MTR_N=400000`), тогда как на базовых
   дисках их два. Повторного перехода в точке `*TRANS` не происходит; печать нашего
   результата не наступает.
4. **ГИПОТЕЗА «компактный E64+дескриптор+GOST в хвосте зоны 0o207» ОПРОВЕРГНУТА.**
   `Э64` второй структуры с адресом `0o46120` кодируется как `0o76120`
   (exp-бит добавляет `0o70000` к младшим 12 разрядам), дескриптора там нет; MTR:
   `MTR 65770L *64 76120(0)`, печать пустая. Диапазон `0o10000..0o67777` адресов
   второй структурой не кодируется, а свободного исполняемого места в зоне 0o207
   всего 8 слов (`0o1770..0o1777`), чего для кода+дескриптора+3 GOST-слов недостаточно.
5. **Попытка самопатча элемента VJM (`сч 0o65772; зп 0o36621`) ОПРОВЕРГНУТА:**
   `сч 0o65772` второй структурой_executes как `xta 75772(0)` (адрес искажён);
   запись в `0o36621` не произошла, Boot ушёл в резидент без нашего результата
   (`runs/stub_patch/em.txt`).
6. **A/B на целевом пути не замкнут:** цель не достигнута, поэтому проверка
   «6→5 даёт 15» на целевом пути невозможна. A/B на прототипе D1 замкнут (§1).

## 5. ТОЧНАЯ ПРИЧИNA BLOCKED

При разрешённом механизме (только бинарный патч диска 2048, без правки C-исходников
dispak) Путь `*TRANS` устроен так:

1. `*TRANS` читает каталог `2148:0o1550`, берёт GOST-баннер из зоны каталога и печатает его
   (поэтому баннер 4.12 исчезнет только при подмене слов баннера в каталоге, но компилятор
   всё равно останется резидентным);
2. тело зоны `N+1` **никогда не копируется в ОЗУ как код/данные** (CORE DIFF §2);
3. переход к компилятору идёт через `VJM 0o455` → `0o64002`; этот элемент собирается из
   единственного слова диска 2048 `0x139388` и патчится, но первый переход происходит при boot,
   а после его подмены повторного перехода в точке `*TRANS` не возникает;
4. исполняемый свободный фрагмент зоны кода монитора — всего 8 слов, а адресация данных
   второй структурой не позволяет указать нужные ячейки ОЗУ (`0o46120` → `0o76120`).

Для полного успеха требуется механизм, который **во время `*TRANS`** (после чтения деки)
одновременно (а) поместит наш 400-словный образ в ОЗУ по `0o1770..` и (б) перехватит
именно второй переход. В чистых бинарных патчах диска это не достигнуто; C3-хук C-кода
решает это, но прямо запрещён правилом пользователя. Продолжение возможно только по
направлению «патч кода загрузчика/монитора на диске, который копирует тело зоны 1551 в RAM
в момент `*TRANS`», либо с отдельным разрешением на C-патч.
