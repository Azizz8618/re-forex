## ВЕРДИКТ: **BLOCKED** (честно: статического boot-image слова не существует)

**Причина блокера (ФАКТ, доказан инструментацией):**
слово по RAM `0o455` **не является статическим словом ни в одном boot/disk-файле**.
Оно **конструируется во время исполнения** монитором: команда `stx 0(0)` по PC `0o64425`
(в резидентном компиляторе, загруженном с логического диска 30 = файл `2048`,
зоны `0o50/0o51/0o52` → физические `0o250/0o251/0o252`, страница `0o64000`)
записывает в `0o455` значение, собранное побайтово циклом `0o64415..0o64427`
через буфер `0o53402/0o53403`. Побайтовый поиск полного слова
`6710000202200000` (и всех перестановок байт) во всех файлах
`/usr/local/share/besm6/*`, `dispak/build/dispak/*`,
`simh/BESM6/MD/*`, `input_queue/*`, `boot_dispak.b6` не дал
ни одного осмысленного совпадения (совпадения `rev` — случайные,
не выровнены по зоне/слову).

Следовательно **невозможно** сделать патч «statical boot image: file:offset:word»,
который при загрузке dispak менял бы VJM по `0o455`. Патч возможен только
на уровне кода, который это слово собирает, либо на уровне самого слова в ОЗУ
до его декодирования. Ниже — точный рецепт такого патча и доказательство,
что CPU реально исполняет перенаправленную команду.

---

## 1. Точное слово по PC 0o455 (ФАКТ)

Дамп ядра на `BESM6_CORE_ON_PC=000455` (копия `runs/base455/core-pc.bin`,
6 байт/слово, big-endian; компьютер `runs/base455/mtr455.err`):

```
00455: 6710000202200000     байты dc 80 02 09 00 00
```

Декод по макросам `defs.h` (`Lreg/Lstruct/Lop1/Laddr1`, активная ветка
`#ifndef WORDS_BIGENDIAN`) и трасса MTR:

```
MTR 00455L vjm    64002(15) AU=... reg=15
ADDRDBG abpc=00455 addr=64002 uiaddr=00002 addrmod=0 MODREG=20
        reg[MODREG]=64000 reg15=53402 ui.reg=15 ui.opcode=111
```

**Разбор слова:**
- левая половина `67100002` (байты `dc 80 02`):
  `Lreg = 0xdc>>4 = 15` (`(15)`), `Lstruct = 0xdc&8 = 8` (1-я структура),
  `Lop1 = 0o11`, `Lopcode = 0o11|0o100 = 0o111` → в `optab[]` индекс `0o111` = `"vjm"`;
  `Laddr1 = ((0x80<<8)|0x02)&0x7fff = 2`.
- эффективный адрес = `ui.i_addr + reg[MODREG=16]` = `2 + 0o64000` = **`0o64002`**.

`reg[16] = 0o64000` — база страницы резидентного FOREX 4.12, выставленная монитором.

## 2. Откуда берётся слово (ФАКТ, инструментация копии cu.c/defs.h)

```
STORE0455 pc=64424 l=00000000 r=00000000      ; обнуление
STORE0455 pc=64425 l=67100002 r=02200000      ; итоговая запись
LOADTARGET pc=64424 addr=53403 bytes=dc8002090000
LOADTARGET pc=64425 addr=53402 bytes=dc8002090000
STORE5340 pc=64421 addr=53403 l=67100002 r=02200000
```

Трасса MTR цикла `0o64421..0o64427` показывает побайтовую сборку
(`xts 66(0)`, `atx 0(17)`, `arx 1574(15)`, `stx`), т.е. слово НЕ лежит в файле
готовым. Источник данных — страница `0o64000`, загружаемая с диска 2048:

```
ZREAD u=30 zone=50 addr=64000  / zone=51 addr=64000 / zone=52 addr=64000
RAWREAD2 disk=2048 zone=250 / 251 / 252   (物理 zona = logical + ZONE_OFFSET=0200)
```

Паспорт задачи: `vol {wr=0, u=030(восьм.), volno=2048, offset=0}` →
логический юнит 30 = файл `2048`. Это подтверждает A2 («диск 30, зона 0o51»).

## 3. Расчёт патченного слова (ФАКТ + ГИПОТЕЗА→проверка)

Нужно, чтобы эффективный адрес стал `0o1770`, сохранив opcode/reg/структуру
(чтобы `vjm` по-прежнему писал `reg[15] = 0o456`, как в C2):

```
(ui_addr + reg[16]) & 0o77777 = 0o1770
reg[16] = 0o64000
ui_addr = (0o1770 - 0o64000) & 0o77777 = 0o15770
```

Проверка: `0o15770 + 0o64000 = 0o77770`; `0o77770 & 0o77777 = 0o1770` ✅

Новое слово (меняем только поле адреса `2 → 0o15770`, байты `80 02 → 9b f8`):

```
БЫЛО:  6710000202200000   байты dc 80 02 09 00 00
СТАЛО: 6711577002200000   байты dc 9b f8 09 00 00
```

Декод патченного слова (C-тест `/tmp/decnew.c`, макросы `defs.h`):
`opcode=111 (vjm), reg=15, addr=15770, struct=10` — те же поля, что у оригинала,
изменён только адрес.

## 4. Патч-копия и проверка на CPU (ФАКТ)

Патч применён к **копии** исходников (`/var/tmp/b1-f77-fix/59-c1/src-dispak/`),
файл `dispak/defs.h`, макрос `STORE`: при записи в `0o455` значения
`l=0xdc8002, r=0x090000` подставляется `l=0xdc9bf8`. Собранная копия:
`src-dispak/build/dispak/dispak`. Живые диски не тронуты.

Прогон на копиях дисков (`runs/patched/`, deck из `59-b2`, `BESM6_PATH=$PWD/disks`):

```
C1PATCH pc=64425 0o455: 6710000202200000 -> 6711577002200000
MTR 00455L vjm    1770(15) ... reg15=00456 → 01770
MTR 01770L atx    0(0)   ... (PC реально дошёл до 0o1770)
CORE DUMPED at pc=00455 -> core-pc.bin
core-pc.bin[0o455] = 6711577002200000    ← патченное слово в ОЗУ
```

**Ответ на замечание C2 про `NEXT;`:** в моём патче слово меняется **до** выборки
и декодирования (на момент `stx` по PC `0o64425`, задолго до перехода на `0o455`).
Поэтому «устаревшего декода VJM 64002» не существует: когда PC становится `0o455`,
CPU fetch'ит уже патченное слово. MTR это подтверждает (`vjm 1770(15)`),
т.е. отдельный `NEXT;` не нужен — в отличие от C2-симуляции, где `pc` менялся
после декода.

## 5. Ограничение: наши 11 слов в RAM 0o1770 (ФАКТ)

Прогон с телом A5 (`runs/c1our/`, harness `a3.py c1our --body-bin a5_static_code.bin:9`,
11 наших слов записаны в body word 9) показал:

```
MTR 01770L atx 0(0) / 01770R atx 0(0) ...   (все нули, НЕ наш *64)
Interrupt 02004 atx
```

То есть при чистом редиректе одним словом **наши слова отсутствуют в RAM 0o1770**:
загрузчик `*TRANS` копирует тело зоны N+1 в `0o1760+` с трансформацией полей
(A2 §1: ни одно слово зоны N+1 не встречается в ОЗУ дословно), а C2 для своего
proof'а был вынужден явно грузить `WORDS=<11 наших слов>` через env-симуляцию.

**Вывод:** даже идеальный патч одного слова `0o455` не заставит наш `*64`
исполниться без дополнительной загрузки наших 11 слов в `0o1770..0o1782`
(тримполин или патч загрузчика `0o701..0o711`). Это отдельная задача (C2/C3).
