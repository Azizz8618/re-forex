# 412 / NEWCOMP*: как грузится FOREX 4.12 и почему SIMH-прогон молчал

Дата: 21.11.2026. Рабочий каталог: `/var/tmp/b1-f77-fix/412-newcomp/`.
Репозиторий `/home/azizz/Yandex.Disk/re-forex` — READ-ONLY, правок и git-записей нет.
Все образы/логи — локальные КОПИИ. Секретов нет.

---

## ВЕРДИКТ

**DONE.** Найдены и подтверждены оба механизма:

1. **Формат параметра `41/1550`.** `NEWCOMP*` берёт из карты `*TRANS:FOREX3*,,411550`
   пару «диск 41 / зона 0o1550», читает **одну зону 0o1550 диска 41** в буфер
   монитора (трасса C-симулятора: `DD pc=03022L ... u=41 z=1550 RD`),
   находит в ней каталог с именами `FOREX3*`, `LO*SYN`, `LO*GEN` и грузит DMS-модули
   оттуда. Это **не** имя модуля на ленте и не имя в `ltable` — это физический
   указатель на диск.

2. **Причина молчания SIMH — ДВЕ независимые ошибки, обе воспроизведены A/B:**
   - (А) SIMH использует не тот образ диска 2148: в `dispak.ini` к `md01`
     приклеен `/home/azizz/Yandex.Disk/simh/BESM6/MD/2148` (SHA `d7f6738e…`),
     а рабочий компилятор лежит в `/usr/local/share/besm6/2148` (SHA `75617c04…`).
     Это **разные диски**, у них все 1015 зон отличаются. В зоне 0o1550 MD/2148
     нет ни `MONITOR*`, ни `FOREX3*`, ни `LO*SYN`, ни `LO*GEN`.
   - (Б) В COSY-'шапке' деки не было `ОЗУ 32^АЦП …`. DISPAK под SIMH принимает
     задачу, но без запроса ОЗУ/АЦП печать не идёт. С правильно приклеенным
     диском, но без этой строки АЦПУ пуст; с ней — баннер 4.12 и `HELLO 412`.

Рабочий рецепт SIMH и C-симулятора — в §5.

## 1. Что именно делает `*TRANS`

**ФАКТ.** `/home/azizz/Yandex.Disk/monitor80-re/permanent/ltable%.asm:37-38`:

```
            , ISO ,6Н*TRANS
            , TEXT,8НNEWCOMP*  .+
```

**ФАКТ.** `monsys.9`, слово `0o423226` = `0o5645674357556012` = TEXT `NEWCOMP*`;
соседи по таблице (`logs/forex3_pointers.txt`): `STACOMP*` `0o423222`,
`DINCOMP*` `0o423224`, `AVTOLOAD` `0o423230`. Дескриптор NEWCOMP* —
слово `0o423227` = `0o7011020004300000` (поле `f1=0o0430`, как у других записей
этой же таблицы: `STACOMP*` → `0o1020`, `AVTOLOAD` → `0o0220`).

**ФАКТ (трасса).** `/var/tmp/b1-f77-fix/412-disp/deck/wt-dd.err:157`:

```
DD pc=03022L r016=53405 u=41 z=1550 RD uil=10/0/300 uir=41/0/1550
```

За 15 строк до неё (`:151`):

```
DD pc=03007L r016=53405 u=30 z=0050 RD uil=10/0/300 uir=30/0/50
```

Расшифровка перевода `wt-trace.run:467-468`:

```
03006: *70 53405 (=0010030000300050) acc=...
03021: *70 53405 (=0010030000411550) acc=...
```

То есть аргумент `*70` — слово `0o0010030000300050` / `0o0010030000411550`:
старшие 12 бит (`0o001003`) — код/счётчик операции, младшие 6 окт. цифр —
**упакованные «диск/зона»** (`30 0050`, `41 1550`). Единственный доступ к
диску 41 за весь прогон — чтение зоны 0o1550.

**ГИПОТЕЗА (обоснованная):** чтение с `u=30 z=0050` — подгрузка самого
`NEWCOMP*` из системной области (диск 30) перед работой; дальше `u=41 z=1550`
читает «библиотеку компилятора». Прямого доказательства на младших слоях
(какая именно-link/COMMON-ячейка) нет: дизассемблировать сам NEWCOMP* не удалось,
он в DISPAK-памяти, а не отдельным DMS-модулем на доступных образах.

## 2. Что лежит в зоне 0o1550 и 0o1551 диска 2148

**ФАКТ.** Команда (обратите внимание: `besmtool` принимает **номер диска**, а не
путь; `--start` — **десятичный** номер зоны, 0o1550 = 872):

```
cd /var/tmp/b1-f77-fix/412-newcomp
besmtool dump 2148 --start=872 --length=1 --to-file=z1550.bin
besmtool view 2148 --start=872 --length=1 --encoding=t,k
```

Слово за словом (`z1550.bin`, big-endian 48 бит):

| Адрес | Слово (восьм.) | TEXT/смысл |
|---|---|---|
| 1550.0000 | `0o5557565164576212` | `MONITOR*` |
| 1550.0001 | `0o0000000000000370` | дескриптор |
| 1550.0002 | `0o4657624570231200` | `FOREX3*` |
| 1550.0003 | `0o0400402757101760` | дескриптор: поля `f3=0400 f2=4027 f1=5710 f0=1760` |
| 1550.0004 | `0o5457126371560000` | `LO*SYN` |
| 1550.0005 | `0o0401423673031551` | дескриптор: `f3=0401 f2=4236 f1=7303 f0=1551` |
| 1550.0006 | `0o5457124745560000` | `LO*GEN` |
| 1550.0007 | `0o0411023634031551` | дескриптор: `f3=0411 f2=0236 f1=3403 f0=1551` |
| 1550.0012..16 | ASCII | `OVERLA` / ` OT  ` / `27.06` / `85 M3 ` / `<<-->>` |

**ФАКТ.** Это **каталог** (пары «имя / 12-битные поля»), а не шапка DMS-модуля.
DMS-шапка начинается на следующей зоне, **1551.0001**:

```
1551.0001  0o4657624570231200  TEXT 'FOREX3*'
1551.0002  0o0003770010073377  set=0o73377 data=0o100 long=0o377
1551.0003  0o0002220000001760  cmd=0o1760 bss=0 const=0o222
```

`dtran -F dms` на файле `forex3_full.dms` (0o113405 слов от 1551.0001)
читает заголовок однозначно:

```
C Commands: 1760     C Constants: 222     C BSS: 0
C Memory size: 2202  C Header: 1200       C Symbols: 7023
C Long symbols: 377  C Debug: 4657        C Data: 100 + set: 73377
C Actual length of the object file is 113405   (= 38 661 слов, ~37.8 зоны)
```

(Полный `dtran` не проходит: лимит программы 32768 слов, модуль 38661 —
`File too large`. Заголовок при этом прочитан корректно.)

**ФАКТ.** Имена спутников внутри того же тела: `LO*SYN` на `1553.0101`,
`LO*GEN` на `1572.0101` (TEXT-сигнатуры `0o5457126371560000` /
`0o5457124745560000` на этих адресах). То есть `FOREX3*`, `LO*SYN`, `LO*GEN`
из каталога 1550.0002/4/6 указывают на DMS-тела в зонах 1551+.

**Сравнение с N2 (PERSO).** Там модуль `N2MRK` имел `head=1 sym=2 long=2
cmd=0o11 const=0o3 f0=0`, `L=cmd+const+bss=12`. Здесь та же схема 3-словной
DMS-шапки, но `head=0o1200`, `cmd=0o1760`, `const=0o222`, и **field-0 у каталожной
записи ненулевой** (`f0=0o1760`). **ГИПОТЕЗА:** `f0` каталожной записи FOREX3*
совпадает с `cmd=0o1760` — вероятно, это длина загружаемой части; у `LO*SYN`/
`LO*GEN` в `f0` стоит `0o1551` (зона). Однозначно не проверено.

## 3. Диск 41: какой файл нужен

**ФАКТ.**

| Файл | SHA256 (16) | Размер | Зона 0o1550 |
|---|---|---|---|
| `/usr/local/share/besm6/2148` | `75617c04fee7d90d…` | 8 379 840 | каталог `MONITOR* FOREX3* LO*SYN LO*GEN` ✅ |
| `simh/BESM6/MD/2148` (приклеен к `md01`) | `d7f6738e15ec605d…` | 8 379 840 | **другие данные**, ни одной из 4 сигнатур ❌ |

Оба файла — SIMH-формат: 1024 зон × (8 служебных + 1024 данных) × 8 байт =
8256 байт/зона; `besmtool`/C-`disk_readi2` добавляют `ZONE_OFFSET=4`, поэтому
физический offset зоны 872 = `(872+4)*8256 + 64 = 0x6E6440`. Все 1015 зон
двух файлов побайтово различны.

**ФАКТ (A/B на C-симуляторе `dispak`, deck `412-disp/deck/t412.b6`):**

- `BESM6_PATH=goodpath` → `good2148.out:29`
  `F О R Е Х ИПМ АН СССР 4.12 ОТ 25.06.85 ВРЕМЯ: 00.00`, в конце `НЕLLО 412`.
- `BESM6_PATH=badpath` (SIMH MD/2148) → `bad2148.out:29`
  `ОТСУТСТВУЕТ  FОRЕХ3*`, `СВОБОД 01770`, `КОНЕЦ ЗАДАЧИ`. Баннера нет.

То есть `NEWCOMP*` ищет имя `FOREX3*` **в прочитанной зоне 41/1550**; если
каталог другой — компилятор не находится.

## 4. Почему SIMH давал «задача принята, АЦПУ пуст»

**ФАКТ (воспроизведено в точности).** Deck без `ОЗУ/АЦП` (копия рабочей C-деки
`412-disp/deck/t412.b6`) при правильном образе 2148, приклеенном к `md01`:

```
шифр 419999 зс5^
DIS 41(2148)^
eeв1а3
...
```

`simh_good.log`: `B075-1 419999000000`, `ОЗ(075) 419999000000`, затем `ЗНЕТ`,
` Changed ACPU: []`; файл `simhwork/disks/output.txt` содержит только
стартовый дамп системы `СБО,ВВЕДИ ПО ИНС` и `*АЦПУ-0`, **ни одного** баннера
или строки программы (`simh_good.log`, `simhwork/disks/output.txt`).

**ФАКТ.** Та же дека + строка `ОЗУ 32^АЦП 64^` + тот же правильный диск →
`simh_good_output.txt` (copied from prn0):

```
:147  F О R Е Х ИПМ АН СССР 4.12 ОТ 25.06.85 ВРЕМЯ:  00.26
:151     3            100 FОRМАТ(′НЕLLО 412′)
:192  НЕLLО 412
:194   КОНЕЦ ЗАДАЧИ        +000000000000⏨+00    0000000000001005
:200   ЗАКАЗАНО:  0032   032    00.10.06      064.00
```

**ФАКТ (контроль).** Правильная дека `newcomp2.deck`, но `md01` → `badpath/2148`
→ `simh_bad.log`: задача `B075-1 419999000000` в ВЦП, АЦПУ опять пуст.

**ИТОГОВАЯ ПРИЧИНА (ФАКТ, A/B в обе стороны):** молчание SIMH объясняется
 simultанно (А) подменой образа 2148 и (Б) отсутствием `ОЗУ/АЦП` в шапке деки.
Устранение любого одного из двух недостаточно. Ошибки разбора карты `*TRANS`
или неверного шифра **не** наблюдались: задача принималась оба раза.

**ГИПОТЕЗА:** в C-симуляторе `dispak` печать работает «по умолчанию для batch
задач» (`-p`, default for batch tasks), поэтому `ОЗУ/АЦП` там не нужны; SIMH-
DISPAK требует явного Operator-подключения АЦПУ к конфигурации задачи
(`ДАЙ А0/A1` + метры АЦПУ в шапке задачи). Отсюда кажущееся противоречие между
успешным whetstone-логом и неудачным SIMH-прогоном.

## 5. Рабочие рецепты

### 5.1 C-симулятор `dispak` (самый простой)

```
cd /var/tmp/b1-f77-fix/412-disp/repro
BESM6_PATH="$PWD/disks" ./dispak t412.b6 > t412.out 2>&1
```

`disks/2148` обязан быть копией `/usr/local/share/besm6/2148` (SHA `75617c04…`).
Дека `t412.b6`:

```
шифр 419999 зс5^
DIS 41(2148)^
eeв1а3
*name T412
*TRANS:FOREX3*,,411550
      PROGRAM MAIN
      PRINT 100
  100 FORMAT('HELLO 412')
      END
*execute
*end file
``````
ЕКОНЕЦ
```

### 5.2 SIMH + `tools/run_besm6_deck.py` (проверено, banner получен)

1. Скопировать `/usr/local/share/besm6/2148` в отдельный файл и в кастомном
   `.ini` (копия `simh/BESM6/OSZAGR/dispak.ini`) заменить строку

   ```
   attach -e md01 ~/Yandex.Disk/simh/BESM6/MD/2148
   ```

   на

   ```
   attach -e md01 /var/tmp/b1-f77-fix/412-newcomp/simhwork/disks/2148-good
   ```

   Важно: в SIMH `DIS 41(2148)` адресует **пак 2148**, который в ini висит на
   `md01`, а не на `md41` (там `EC5061/2070`).
2. Дека (`simhwork/newcomp2.deck`) — та же, но с обязательной второй строкой:

   ```
   ШИФР 419999 ЗС5^
   ОЗУ 32^АЦП 64^дис 41(2148)^
   EEВ1А3
   *NAME T412
   *TRANS:FOREX3*,,411550
         PROGRAM MAIN
         PRINT 100
     100 FORMAT('HELLO 412')
         END
   *EXECUTE
   *END FILE
   ``````
   ЕКОНЕЦ
   ```

3. Запуск (например, с изолированными принтерами):

   ```
   python3 tools/run_besm6_deck.py --deck .../newcomp2.deck \
     --ini .../simhwork/deck.ini --cipher 419999 --acpu 64 --timeout 240
   ```

Результат сохранён в `simh_good_output.txt`: баннер 4.12 `ОТ 25.06.85`,
листинг, `НЕLLО 412`, `КОНЕЦ ЗАДАЧИ`.

## 6. Что осталось непроверенным

- Дизассемблировать сам `NEWCOMP*` (PC 0o03000-0o03022) и доказать, какие именно
  LINK/COMMON-ячейки монитора он использует: отдельного DMS-модуля с таким
  именем на доступных лентах/дисках нет, только запись в STABLE `monsys.9:0o423226`.
- Прочитать младшие 12-битные поля каталожных записей 1550.0003/5/7 как
  «адрес и длина» — версия с `f0=cmd` правдоподобна, но не доказана.
- Проверить, можно ли подсунуть своё тело в другой зоне (план 58 / M3/M4):
  для этого нужно, чтобы каталог в зоне 41/N содержал имя, которое ищет
  `NEWCOMP*`, и DMS-тело по тому же формату. Готовый A/B-тест с подменой
  зоны в копии 2148 — следующий шаг, в эту задачу не входил.
