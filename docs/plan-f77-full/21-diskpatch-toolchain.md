## 1. Формат диска 2348, который использует инструмент

Физический формат — «new format» из `dispak/dispak/disk.h` (`zone_t`), подтверждён
по `disk_readi2()/disk_writei2()` и по факту (размер файла 33 024 000 = 4000 × 8256):

| Уровень | Значение |
|---|---|
| Физическая зона | 8 служебных слов (`z_cwords`, uint64) + 1024 информационных слова (`z_data`, uint64) = **8256 байт** |
| Слово на диске | **8 байт**, uint64 native-endian; рр. 0..47 — 48-битное слово БЭСМ-6, р. 48 — свёртка, рр. 49..63 — служебные |
| Логическая зона `L` | физическая `L + 4` (`ZONE_OFFSET`), смещение файла `(L + 4) × 8256`. Так, `0o2300` (1216) → физическая 1220 → смещение 10 063 360 |
| Число зон | 4000 физических = логические `0..3995` (физ. `0..3` — служебные) |

Логический «6-байтовый» формат `besmtool dump/write` (ZBYTES=6144) — это то же
самое содержимое без uint64-обвязки: `disk_readi2()` упаковывает 6 байт в младшие
48 бит uint64. Инструмент работает с **физическими байтами файла**, поэтому видит
как информационные, так и служебные слова (контрольные суммы) без потерь.

## 2. CLI

```
python3 tools/patch_system_disk.py snapshot <disk> <out.json>
python3 tools/patch_system_disk.py apply   <disk> <patch.json> <out-disk> \
        [--zone-mode=logical|physical] [--fix-checksum]
python3 tools/patch_system_disk.py verify  <disk> <snapshot.json> [reference-disk] \
        [--json-out <file>] [--strict]
```

Полный help — в `logs/f77_21_tool_cli.txt`.

### 2.1 `snapshot <disk> <out.json>`

Фиксирует эталон: sha256 всего файла + sha256 **каждой** физической зоны (все
8256 байт, включая 8 служебных слов). В JSON сохраняются путь к диску, размер,
sha256 файла, описание формата и таблица `{"0": "<sha>", ...}` для всех 4000 зон.
Это и есть «точка отката»: если эталон на диске изменится, `verify` это увидит.

### 2.2 `apply <disk> <patch.json> <out-disk>`

Применяет список патчей **только к копии**:

- исходный `<disk>` открывается на чтение и **никогда не перезаписывается**;
- запись идёт во временный файл рядом с `<out-disk>` → `fsync` → `os.replace`
  (атомарно); при любой ошибке временный файл удаляется, `<out-disk>` не создаётся;
- `<disk>` и `<out-disk>` не могут быть одним файлом (явная проверка);
- **обязательна проверка `old`**: несовпадение прерывает весь патч до записи;
- дублирование одной и той же `(зона, слово)` запрещено;
- после записи повторно проверяется sha256 исходного диска;
- при записи сохраняются старшие биты физического слова (свёртка), меняются
  только младшие 48 бит;
- `--fix-checksum` пересчитывает `z_cwords[3]/[7]` затронутых зон по алгоритму
  `disk_writei2()`. По умолчанию **выключено**, чтобы патч был минимальным
  (иначе в `verify` появятся ещё 2 изменённых служебных слова на зону).

### 2.3 `verify <disk> <snapshot.json> [reference-disk]`

Побайтовая сверка:

1. сравнивает sha256 файла и по зонам — находит **изменённые зоны**;
2. если доступен эталонный файл (3-й аргумент или путь из snapshot, при условии,
   что его sha256 совпадает с зафиксированным) — читает обе зоны и сравнит слово
   за словом, печатая **изменённые слова** с адресом и значениями `old → new`
   (для информационных слов и для `cword`);
3. Если нет эталона — честно печатает только изменённые зоны (`слов: ?`).

Вывод: `STATUS: IDENTICAL|CHANGED`, счётчики зон/слов и список.
`--json-out` даёт машиночитаемый отчёт, `--strict` возвращает rc=2 при изменениях
(по умолчанию rc=0 — «сверка выполнена», чтобы не ломать RPG-скрипты).

### 2.4 Формат патча и числа

```json
[
  {"zone": "0o7000", "word": "0o1777", "old": "0", "new": "0o1234567"}
]
```

| Поле | Смысл |
|---|---|
| `zone` | логический номер зоны (как в `besmtool` / `0o2300`); `--zone-mode=physical` — физический |
| `word` | номер информационного слова, 0..1023 (`0o0`..`0o1777`) |
| `old` | **обязательное** ожидаемое 48-битное значение (проверка до записи) |
| `new` | новое 48-битное значение |

Числа: `int` = десятичное; `"0o.."` / `"0x.."` / `"0b.."` = с префиксом; строка
из цифр = десятичное. В репозитории зоны принято писать восьмеричными (`0o2300`),
поэтому в патчах рекомендуется `0o`-префикс.

Лог: `logs/f77_21_selftest.txt`, машиночитаемый отчёт — `/var/tmp/p7c-diskpatch/verify.json`.

### 3.1 Что делали

1. `snapshot /usr/local/share/besm6/2348` → эталон зафиксирован:
   `sha256 = 30fd6355b25d9ed3f06f57d84a3eac6ecfde2d6d5b7d34b1c27a7b44a6513152`,
   33 024 000 байт, 4000 зон.
2. `cp` эталона в рабочую копию `2348.work`.
3. Фиктивный патч в **свободной зоне `0o7000`** (все 1024 информационных слова
   нулевые, зона не используется ни одной декой регрессии), слово `0o1777`:
   `0 → 0o1234567`.
4. `apply 2348.work patch.json 2348.patched`.
5. `verify 2348.patched etalon.snapshot.json /usr/local/share/besm6/2348`.

### 3.2 Результат verify — ровно одно слово

```
STATUS            : CHANGED
изменённых зон    : 1
изменённых слов   : 1
ЗОНА  0o7000 (phys 0o7004)
СЛОВО зона 0o7000 (phys 0o7004) word 1023 (0o1777) [data]:
      0o0 -> 0o1234567 (u64 0x2000000000000 -> 0x2000000053977)
```

**Список изменённых слов (итог):**

| Зона (лог. / физ.) | Слово | Было | Стало | Тип |
|---|---|---|---|---|
| `0o7000` / `0o7004` | `0o1777` (1023) | `0o0` | `0o1234567` | информационное |

Старшие биты слова (`0x2 << 48`, признак свёртки) **сохранены** — изменились
только младшие 48 бит. Контрольные слова зоны не тронуты (`--fix-checksum` не
использовался), поэтому изменение действительно ровно одно слово.

### 3.3 Дополнительные проверки

- `verify 2348.work ...` (непатченная копия) → `STATUS: IDENTICAL`, 0 зон, 0 слов.
- sha256 эталона **до и после** всех операций одинаков
  (`30fd6355…3152`) — эталон не изменён.
- Негативный тест: патч с неверным `old=0o777` → `ОШИБКА: old НЕ СОВПАЛ`,
  rc=1, выходной файл **не создан**.
- Дополнительно проверено: неверный номер зоны/слова и дублирование патчей отклоняются.

## 5. Рецепт: безопасно патчить и откатываться

```bash
cd /home/azizz/Yandex.Disk/re-forex
TOOL=tools/patch_system_disk.py
WORK=$(mktemp -d /var/tmp/diskpatch.XXXXXX)     # НЕ в эталонном каталоге

# 1. Зафиксировать эталон (делается ОДИН раз, до любых патчей)
python3 $TOOL snapshot /usr/local/share/besm6/2348 "$WORK/etalon.snapshot.json"

# 2. Рабочая копия — ВСЕГДА копия, эталон не трогаем
cp /usr/local/share/besm6/2348 "$WORK/2348.work"

# 3. Патч (old — обязателен; адреса в восьмеричной нотации)
cat > "$WORK/patch.json" <<'EOF'
[{"zone":"0o7000","word":"0o1777","old":"0","new":"0o1234567"}]
EOF

# 4. Применить: результат пишется в НОВЫЙ файл, atomically
python3 $TOOL apply "$WORK/2348.work" "$WORK/patch.json" "$WORK/2348.patched"

# 5. Проверить, что изменилось ровно то, что хотели
python3 $TOOL verify "$WORK/2348.patched" "$WORK/etalon.snapshot.json" \
    /usr/local/share/besm6/2348 --json-out "$WORK/verify.json"
#   ожидаем STATUS: CHANGED, 1 зона, 1 слово, нужный old -> new

# 6. Прогнать регрессию на пропатченной копии
ETALON="$WORK/2348.patched" bash tests/run-f77-full.sh
#   обязателен GATE 20/20, RC=0

# 7. Промоушн (если нужно): только после шагов 5-6 скопировать
#    пропатченный файл туда, где его ждёт dispak (например в BESM6_PATH-dir):
#    cp "$WORK/2348.patched" /path/to/work/2348
```

**Откат.** Варианты по приоритету:

1. **Самый простой** — удалить/переименовать `<out-disk>` и продолжить с
   `2348.work` или со свежей `cp` эталона. Эталон остаётся незатронутым.
2. Инверсный патч: поменять `old` и `new` местами в `patch.json` и применить его
   к `2348.patched` → получить бит-в-бит исходную копию; проверить
   `verify ... → STATUS: IDENTICAL`.
3. Восстановить из snapshot: `cp /usr/local/share/besm6/2348 <disk>` и сверить
   `sha256sum` с `file_sha256` из snapshot.

**Контрольные точки безопасности:**

- никогда не указывайте один и тот же путь в `apply <disk>` и `<out-disk>`;
- после apply всегда сверяйте `sha256` эталона — он не должен измениться;
- для «настоящего» патча в используемой зоне добавьте `--fix-checksum`, чтобы
  контрольная сумма зоны не расходилась (но тогда `verify` покажет 1 слово + 2 cword);
- фиктивный self-test делает патч только в свободной зоне и **без** `--fix-checksum`.

## 6. Рекомендации по интеграции в рабочий процесс

1. **Держать snapshot в репозитории** (маленький, ~310 КБ на 4000 зон) вместе с
   деками/патчем: это позволяет в любой момент доказать, с какого эталона начинался
   патч, и автоматически найти расхождения.
2. **Патч — это данные, а не ручная правка.** Хранить `patch.json` рядом с deck,
   ревьюить как код. Поле `old` превращает патч в «expectation»: если эталон
   изменился, патч упадёт, а не испортит диск молча.
3. **В CI добавить шаг** между `cp эталона` и `besmtool write PERSO`:
   `verify (post-write copy) snapshot` должен показывать только ожидаемые зоны
   PERSO (0o2300..0o2304 / 0o2310) — всё остальное должно быть IDENTICAL.
4. **Перед промоушном прогонять `run-f77-full.sh`** с `ETALON=<patched>`; требовать
   `GATE 20/20, RC=0`. Это дешёвый (~10 с) фильтр от случайной порчи системных зон.
5. **Не патчить зоны 0..3 (физ.) и системные зоны монитора/libra** без `--fix-checksum`
   и отдельного обзора — тамошняя контрольная сумма используется при чтении.
6. Для отладки можно дать машиночитаемый `--json-out` у `verify` и подключить его
   к отчёту P7: он содержит список каждого изменённого слова с адресом и значением.

## 7. Ограничения

- Инструмент понимает только **новый** формат диска (`disk.h:zone_t`, 8256 байт/зона).
  Старый формат (6144 байт/зона) явным сообщением отклоняется (`check_size`).
- `verify` может показать отдельные слова только при наличии эталонного файла;
  один snapshot без файла даёт точность до зоны. Это компромисс ради компактного
  JSON (310 КБ вместо 33 МБ дампа).
- Числа `old`/`new` — 48-битное слово БЭСМ-6; старшие биты физического uint64
  (свёртка) сохраняются и в патче не задаются. Для правки служебных слов зоны
  используйте `--fix-checksum` или напрямую `besmtool` (не входит в задачу инструмента).
