# 26 — P7c / ВОЛНА E / ЗАДАЧА 3: может ли Fortran-рантайм читать/писать LUN, объявленный картой `*FILE`

**Дата:** 19.11.2026. **Статус:** ИССЛЕДОВАНИЕ ЗАВЕРШЕНО (прогоны выполнены).
**Главный ответ: НЕТ.** Готовыми мониторными средствами (карта `*FILE`, `лен 41(...)`,
`*perso:602300`) `WRITE(41,10)` и `READ(41,10)`/`READ(41)` **не работают** — во всех
вариантах `НЕТ КАНАЛА LUN 41` и STOP `*74` до выдачи `Э70`.

**Владение.** READ-ONLY: `re-forex/src/`, `re-forex/tests/`, `REFERENCE`, эталоны
`/usr/local/share/besm6/{2048,2348}`, `monitor80-re/`, `dispak/`, `besm6-new/`.

## 1. Полный путь `WRITE(41,10) 123` → физический носитель

```
Fortran WRITE(41,10) 123            (FOREX 2.02, компилятор 0o2300)
  └─ WRITE1.mad:104 CALL,DRUMTAP*   re-forex/src/lib21/WRITE1.mad:39,104
     ├─ SWRITE/SREAD (LUN,AB,AE,COD) → FMRTAPE  src/lib21/SWRITE.mad:33-63
     ├─ IOCONT* / IOEND* / FT*002    monitor80-re/permanent/iocont%.asm:72,137-170,163
     │    └─ SETLUN*                  iocont%.asm:373-377 (22B→113B/107B, внутренняя привязка)
     ├─ низкий уровень: биты 1-6 = LUN, 42-47 = READ/WRITE/REWIND/ENDFILE
     │                               monitor80-re/permanent/ioxxfmr%.asm:6-31
     └─ DRUMTAP*                     monitor80-re/permanent/drumtap%.asm:1-48
          ├─ ячейки LUN 22B/24B/23B/25B, проверка «нет места» :15-40
          ├─ Э70 (обмен с каналом)    — выдаётся ТОЛЬКО после проверки Level B
          └─ при отказе → НЕТ КАНАЛА:
               erriom.asm:47-48  TNETKAN = "НЕТ КАНАЛА", TLUN = "  LUN"
               erriom.asm:84-93  ERRLUN → вых*ERRIOM → LUN*MON (iocont%.asm:66)
                                  → в*STOP → *74
```

* **Где проверяется «юнит заказан»:** не в Fortran-рантайме и не в `LUNTYP`, а в
  **оверлее Монитора-80** (`erriom.asm` → `ERRLUN`), по таблице допустимости LUN в
  памяти `0o02200..0o02273` (§2.3). Это Level B; Level A — `disks[]` хоста
  (`dispak/input.c:61-79`, `defs.h:77-82`) — проверке предшествует и её прохождение
  ничего не меняет.
* **Откуда имя/режим/Position:** в рантайме Fortran их **нет**. `ioxxfmr%.asm:6-31`
  несёт только номер LUN и код операции; `iocont%.asm:26-39,709-715` — шаблон
  диагностики `LUN/SPECIFICATION/FORMAT/ADDRESS`, без поля `FILE/NAME`. Позиция
  (текущая зона) живёт в управлении каналом/носителе (`Э70`), а не в `*FILE`:
  `SWRITE.mad:33-63` передаёт `(LUN,AB,AE,COD)` — адреса буфера и код, но не имя.
  Поэтому «имя файла из `*FILE`» недостижимо из `WRITE(41,...)` при любом исходе.

## 2. Как `*FILE` попадает в таблицы монитора (и чем это не наша таблица)

### 2.1 Дубна (родная среда карты): есть готовый механизм, но это ДРУГАЯ ОС

* Карту разбирает монитор Дубны: `besm6.github.io/sources/dubna/besml21/libra211.l21:5183`
  (диспетчер `*FILE`), **`:5624-5719`** — обработчик `TAK FILE`: `PARAMT*` — имя (п. 3),
  указатель/LUN (п. 4), режим `R`/`W`/`C` (п. 5), число дорожек (п. 5), обязательна
  предшествующая карта `*DISC` (`:5718-5721`, `DINA`), иначе `НЕ ОБ'ЯВЛЕН ДИСК ПЕРЕД *FILE`.
* Структура — **четыре параллельных массива по 32 слова** `*ORDEN`
  (`libra211.l21:141-144`, объявление `:5071-5074`):
  `TAPES/TAP(32)` — характеристики, `TAN(32)` — имена МЛ/ДП, `NAFA(32)` — имена файлов,
  `BOSS(32)` — имена хозяина. Coordinates запроса файла описаны в `:500-535`.
* Эмулятор Дубны (`besm6-new/dubna`) получает это через экстракод `Э57 77777 FILE_OPEN`
  (`e57.cpp:209-234`) → `machine.file_mount()` (`machine.cpp:567-600`) → `Disk` с
  `volume_id=0` = именованный host-файл (`disk.cpp:48-73`).
* В Дубне это **реально работает** как игровая карта: `dubna/tests/expect_file_write.txt:28-38`
  (`ФАЙЛ 41 :ЗАПИСАНО 4 КАРТ`), `expect_file_read.txt:28-38`, `session_test.cpp:846-895`.
  Но Fortran там пишет в 41 **не через `WRITE(41,10)`**, а через библиотечный API
  COSY: `WBEGIN(410000в)/WRCARD/WRIEND`, `RBEGIN(410000в)/RECARD`
  (`dubna/examples/wrcard.dub:8-59`). Это **не J2**, а новый вызов уровня `WR/ВТ`.
  Аналог в нашем рантайме — символы `WR/ВТ`/`RD/ВТ` в таблице символов задачи.

### 2.2 Монитор-80 (реконструкция): карта есть в исходнике, но в_TASK рантайм не попадает

* `monitor80-re/chekjob/g02407.f:53-54` — `*FILE` в таблице `k552`; ветка `:196-208`
  → `G04720(CARD,k550)` (`g04720.asm:1-101`) → `G05634` (`g05634.asm:1-67`, `*50,156B`)
  + `G04052/G04066` контроль дублей LUN; `HANDLE` — заглушка (`handle.asm:1-4`).
  Вызывается из `CHEKJOB*` (`chekjob/chekjob.asm:33-35`) **до** загрузки программы.
* Таблицы: `monitor%.asm:86` `IODCB*:LC,31` (инициализация `SETIODCB` из статического
  `tabiodcb`, `setiodcb.asm:7-44`), `:87` `TAPELIST:LC,25`, `:92` `*REGIM//`,
  `:94` `MONCARD*:LC,25`, `:97` `IOLIST*:LC,5`, `:98` `*IOXLCB*`.
  `LUNTYP` только **запрашивает** тип через `*63 502/504/…` (`LUNTYP.mad:60-90`).
  Таблицы «имя файла → LUN» в рантайме **нет** — подробнее `24-file-card-monitor.md:§2-5`.

### 2.3 Фактический dispak-стенд: наша таблица `0o02200..0o02273` — НЕ `*ORDEN` и НЕ `TAPELIST`

Формат (дамп супервизора, `22-errlun-supervisor.md:98-115`; проверено мной):

* одно 48-битное слово на LUN, база `0o2200`对应 LUN 4 ⇒ адрес = `0o2200 + (LUN-4)`;
* слово `[A=24 бита][B=24 бита]`: `A = LUN + 0o100`, `B = [флаги][LUN в восьм.]`;
* три копии на дисках 2048 и 2348: логические зоны `0o212 / 0o403 / 0o422`,
  для LUN 45 — слова `5 / 0o332 / 0o1532`.

| LUN | память | ядро (core_err.bin) | зона 0o212, слово | зона 0o403 | зона 0o422 |
|---:|---|---|---|---|---|
| 41 | **0o2245** | `0000692c0029` = `0o15113000051` | 1 (`0o15113000051`) | 214 (`0o326`) | 854 (`0o1526`) |
| 45 | 0o2251 | `00006d0d002d` = `0o15503200055` | 5 (`0o15503200055`) | 218 (`0o332`) | 858 (`0o1532`) |

(Лог `logs/f77_24_runtime_luntab.txt`.) Это таблица **допустимости/типа канала
Монитора-80**, рабочая: в неё пишут `03765R`, `00703L`, `03546L` и др.; на момент
старта она обнулена (`core_full.bin` — нули), к моменту ошибки — заполнена.
Она **не** заполняется картой `*FILE` (dispak её не разбирает, §3) и **не** тождественна
дубнинскому `*ORDEN` (там 4×32 слова имён/характеристик, здесь 1 слово на LUN).

Важное наблюдение: у **LUN 41 уже стоит флаг `0o13`** (у LUN 45 — `0o03`), т.е.
таблица и так содержит запись, которую в `22-errlun-supervisor.md:134` пытались
«подставить» патчем LUN 45 — и это **не снимает отказ**. Значит blocker не только
в битах этой ячейки: нужна правка уровня инициализации/каналов и самого кода
`ERRLUN`/`IOCONT*` в перезагружаемом оверлее, т.е. пересборка монитора и системного
диска 2348 (подтверждено runtime-poke экспериментом `22-...:140-143`).

## 4. READ(41,...) и EOF

| Дек | Карта/юнит | rc | Результат |
|---|---|---:|---|
| `r41_fmt.b6` | `лен 41(2048)^`, `READ(41,10) X` | 0 | `НЕТ КАНАЛА LUN 41`; `GOT X` нет |
| `r41_unfmt.b6` | `лен 41(2048-wr)^`, `READ(41) X` | 0 | `НЕТ КАНАЛА LUN 41`; `GOT X` нет |
| `r41_file.b6` | `*FILE:FUBAR,41^`, `READ(41,10) X` | 0 | `Unknown passport entry` + `НЕТ КАНАЛА LUN 41` |
| `r54_fmt.b6` | `READ(54,10) X` | 0 | `КОНЕЦ ЗАДАЧИ`, `04432 *71`; данных нет |
| `r1_fmt.b6` | `READ(1,10) X`, карта `123.45` | 0 | `05321 *70`; `GOT X` нет |
| `r1_noperso.b6` (контроль, без `*perso`) | безъюнитный `READ 10,X`, 3 карты | 0 | `1 1.50 / 2 2.50 / 3 3.50`, `КОНЕЦ ЗАДАЧИ` — ввод работает |
| `r41_noperso.b6` | то же, но `READ(41,10)` | 0 | `НЕТ КАНАЛА LUN 41` |
| `r41_file_noperso.b6` | `*FILE:FUBAR,41^` + безъюнитный READ | 0 | `Unknown passport entry` + 3 карты прочитаны (`1.50/2.50/3.50`) |
| `r41_file_noperso2.b6` | `*FILE:FUBAR,41^` + `READ(41,10)` | 0 | `Unknown passport entry` + `НЕТ КАНАЛА LUN 41` |

**Где возникает EOF.** Единственный нативный EOF-сигнал — аппаратный
`Э60`: `reg[016]=0` при исчерпании очереди карт (`dispak/input.c:110-151`, см.
`19-eof-iostat.md:§1`). В рантайме он **теряется**: `monread%.asm:99-104`
(`вMOНИTOP → STOP* → LUN*MON`) превращает его в `*END FILE / КОНЕЦ ЗАДАЧИ` rc=0,
без возврата в Fortran. Контрольный прогон `r1_noperso`: 4-й READ после трёх карт
печатает `КОНЕЦ ЗАДАЧИ`, но **не** `AFTER-EOF` — ветвление невозможно. Для LUN 41
EOF недостижим вообще: отказ происходит раньше, в `ERRLUN`, до выдачи Э70/Э60.
`READ(54)` даёт `*71`, `READ(1)` с явным юнитом даёт `*70` — это не EOF, а отказы
режима/экстракода (`15-io.md:45-46`). Итог: `END=`/`IOSTAT=` требуют правки
`monread%`/`IOEND*` и отдельного проекта (`19-eof-iostat.md:§2,§4`).

## 5. VERDICT по J2 / J4 / J23 и что закрывается готовым `*FILE`

| Элемент | Готовыми средствами (без правки монитора) | Что именно нужно |
|---|---|---|
| **J2** `WRITE(u,fmt)`, u=41 | **NO** (`NEEDS-RUNTIME-REBUILD`) | правка/пересборка оверлея `erriom.asm`/`iocont%.asm` и таблицы Level B в 2348; одна запись в 0o2245 insufficient (§2.3). Алиасирование на 54 — только profile convention, не J2 (`17-lun-p7c.md:§4`) |
| **J4** `READ(u,fmt)` | **NO** | то же + EOF/IOSTAT в `monread%.asm`/`IOEND*` (сейчас EOF → STOP) |
| **J23** неформатированный I/O с данными | **NO** (синтаксис OK,transfer blocked) | то же; `WRITE(41) X`/`READ(41) X` дают `НЕТ КАНАЛА` |
| `*FILE` в Dubna + COSY API | **OK как механизм ДРУГОЙ ОС** | не переносится на FOREX: в dispak карты нет, в Monitor-80 нет runtime-имени файла; это новый вызов типа `WR/ВТ`, не J2 |

**Что уже закрыто готовым механизмом:** только *IDEЯ* стартовой декларации LUN
(в Дубне — `*FILE` + `*ORDEN` + `Э57 FILE_OPEN`, в Мониторе-80 — `*FILE` в
`CHEKJOB`/`TAPELIST`/`IODCB*`). В нашем стеке (dispak + FOREX 2.02) рабочего I/O
через неё **не получается**: dispak карту не понимает, а таблица Level B и
`ERRLUN` блокируют юнит 41 даже при смонтированном `лен 41(2048-wr)`.

**Что требует достройки (уровень Monitor-80, без C-правок dispak):**
1. регистрировать LUN 41 в таблице допустимости в **коде инициализации оверлея**
   (не только патч трёх копий зон 0o212/0o403/0o422) и снять early-отказ в
   `ERRLUN`/`IOCONT*`, затем пересобрать системный диск 2348;
2. связать declaration с реальным носителем на уровне мониторного `DRUMTAP*`/`Э70`
   (уровень A уже монтируется `лен 41(...)`);
3. для J4 — вернуть EOF из `monread%` в `IOEND*`/рантайм вместо `STOP*`;
4. регрессия золотых бинарников + gate 20/20.
Оценка по предыдущим волнам — «десятки чел.-дн.» (`17-lun-p7c.md:§7`), дешёвого
патча `LUNTYP` недостаточно (`23-luntyp-patch.md:5-9,76-95`).
