## 0. Вопрос и краткий ответ

**Вопрос.** Как dispak сигнализирует конец входной очереди (конец карт) Fortran-программе,
есть ли признак EOF в слове/флаге, где он теряется, и как дешевле всего передать EOF
в `END=`/`ERR=`/`IOSTAT=`?

**Ответ (одним абзацем).** Признак EOF **есть и он аппаратный**: `Э60` (`input.c:e60()`)
при исчерпании очереди карт пишет `reg[016] = 0` — тот же регистр, который перед вызовом
содержал адрес буфера. Инструментированный прогон это подтверждает:
`TRACE e60: EOF-lastcard ... reg16=0`. Но выше по стеку **`monread%` превращает EOF в
завершение задачи** (переход `вMOНИTOP → STOP*`), не возвращая статус в рантайм; у рантайма
`IOEND*`/`IOCONT*` нет ячейки статуса. Поэтому нативный «EOF» — это `*END FILE / КОНЕЦ ЗАДАЧИ`
при `rc=0`, а не ветка в Fortran. Дешевле всего (0 слов в оверлеях, уже исполняемо) —
**сентинная карта-ловушка** с сравнением первой переменной; именно её и фиксируем как
соглашение профиля. Истинная F77-семантика требует правки системной зоны 2348 — отдельный,
дорогой проект.

## 1. Механизм EOF в dispak (задание 1)

### 1.1 Host-уровень: `Э60` и флаг `reg[016]=0`

`dispak/dispak/input.c:110-151`, функция `e60()` — читает 24 слова из файла входной очереди
`~/.besm6/input_queue/NNN` в `core[reg[016]+i]`:

| Строка | Код | Смысл |
|---|---|---|
| 116 | `if (reg[016] == 0) return E_SUCCESS;` | уже в состоянии EOF — короткий возврат |
| 119 | `if (ftell(ibuf)==enda3) { reg[016]=0; return; }` | **EOF до чтения**: указатель в конце файла |
| 132 | `fread(ibw, …, 24)` | чтение очередной карты (24 слова) |
| 145-147 | `if (pos==enda3) { fseek(ibuf,psp.arr_end,SEEK_SET); reg[016]=0; }` | **EOF после чтения последней карты** |

**Признак EOF = `reg[016] == 0`** (однобитный флаг, совмещённый с регистром адреса буфера).
`Э70`/`ddio()` (`extra.c:2063-2328`) такого флага не имеет — это обычная запись/чтение зоны диска/барабана (extract-code обмена)
диска/барабана; `cu.c:799-834` только подставляет `reg[016]=1` для «дубнинского» варианта
управляющего слова. То есть EOF живёт **исключительно на уровне `Э60`/очереди карт**.

### 1.2 Инструментальный proof (копия dispak в `/tmp`)

В `input.c` копии вставлены `fprintf(stderr,"TRACE e60: … reg16=0")` в обе ветки 119/145;
сборка `cmake … && make dispak` в `/tmp/.../eof/bin-instr/` — rc=0. Прогоны на копии 2348:

| Дек | Карт | Трейс |
|---|---|---|
| `read3_then_eof.b6` | 3 + 4-й READ | `TRACE e60: EOF-lastcard pos=5080 enda3=5080 buf=2052 -> reg16=0` |
| `read1_nodata.b6` | 0 | `TRACE e60: EOF-lastcard pos=3352 enda3=3352 buf=2052 -> reg16=0` |
| `eof_sentinel.b6` | 3 + сентинал | `TRACE e60: EOF-lastcard pos=5272 enda3=5272 buf=2052 -> reg16=0` |

Контекст трассировки (`BESM6_DD_DEBUG=1`) показывает, что флаг выставляется сразу после
`Э70` чтения карты LUN 45 в `monread%`:

```
E70at 00725L r016=00001 uil=70/45 uir=102/0
DD pc=00726L r016=00045 u=20 z=0004 RD ...       <- monread%: чтение карты (Э70, LUN 45)
TRACE e60: EOF-lastcard ... reg16=0               <- очередь исчерпана
(дальше — записи в LUN 1/46 и STOP: задача завершается)
```

### 1.3 Где сигнал теряется: `monread%` → `STOP*`, а не возврат в Fortran

`monitor80-re/permanent/monread%.asm` (стандартная программа МС ДУБНА, исходник утрачен):

- `34/54`: `M15,*70,1` — чтение карты Э70 в `MONCARD*`;
- `55-73`: разбор карты (`AEX 57B`, `AAX 60B`, `U1A NO*END`, `COZUТISO` — перекодировка);
- `99-104` (`вMOНИTOP`): `ITS M6 / M13,VTM,STOP* / UJ,LUN*MON` — **переход в монитор на STOP**;
- `119`: `TNO*END: ISO,12НNO *END FILE` — диагностика отсутствия `*END FILE`.

`monitor80-re/permanent/iocont%.asm`: `IOCONT*` — «пользовательская процедура для продолжения
ввода-вывода», `IOEND*` — `ENTRY` по окончании формата (строки 1-5, 56, 163-180); `STOP*` —
импортированный `SUBP`. **Ячейки статуса ввода/ветки по EOF нет.** В `re-forex/src/lib21/LFSCAN.mad:89-94`
`IOCONT*`/`IOEND*` объявлены внешними `SUBP` — транслятор 2.02 не порождает `END=`/`ERR=`/`IOSTAT=`
(нативная форма `READ(5,10,END=99)` → `ОТСУТСТВ ЗАКРЫВ СКОБКА`, `15-io.md:132`).

**Итоговая цепочка:**

```
очередь карт (input_queue/NNN)
   └─ Э60: reg[016]=0            <- ЕДИНСТВЕННЫЙ EOF-флаг (доказан трассой)
        └─ monread% (Э70 LUN45 → разбор)
             └─ при EOF: вMOНИTOP → STOP*     <- СИГНАЛ ТЕРЯЕТСЯ ЗДЕСЬ
                  └─ *END FILE / КОНЕЦ ЗАДАЧИ (rc=0), без возврата в READ
```

### 1.4 Эмпирическое подтверждение (без инструмента)

| Дек | Что сделано | Вывод |
|---|---|---|
| `read3_then_eof.b6` | 3 карты, 4-й `READ` | `1.50 / 2.50 / 3.50 / *END FILE / КОНЕЦ ЗАДАЧИ`; **нет** `AFTER-EOF`; rc=0 |
| `read1_nodata.b6` | 1 `READ`, 0 карт | сразу `*END FILE / КОНЕЦ ЗАДАЧИ`; **нет** `GOT X`; rc=0 |

То есть честный нативный EOF = **завершение задачи**. Ветвление по нему невозможно ни через
`END=`, ни через `IOSTAT=` — их просто нет в сгенерированном коде.

## 2. Оценка трёх каналов передачи EOF (задание 2)

| Канал | Механизм | Цена | Что даёт | Вердикт |
|---|---|---|---|---|
| **(а) Fortran-обёртка в PERSO 0o2320** | МАДЛЕН-процедура (`*perso:602320,cont`), умеет сырые экстракоды; механизм Fortran→PERSO→`Э50/Э70` доказан в `17-lun-p7c.md §2` (`САLL ОК`) | 1 зона PERSO, ~десятки слов; но **переписывать formatted READ в МАДЛЕН неподъёмно** | Нестандартный вызов наподобие `ISTAT=FGET(...)`: процедура сама читает карту и возвращает `reg[016]==0` как статус | **Механизм OK, но не закрывает J4/J23.** Несовместим с рантайм-`READ*` (тот уже завершает задачу на EOF) и с его буферизацией; годится только как **новый I/O API**, а не как `READ(…,IOSTAT=)` |
| **(б) Сентинал в DATA-карте** | Host дописывает карту-ловушку; Fortran сравнивает первую переменную. Уже работает в J7/J8 (`15-io.md §4.3`) | **0 слов**, 0 правок диска, готовый прототип | Исполняемая эмуляция `END=`/`ERR=`/`IOSTAT=` с оговоркой «по значению» | **ВЫБРАН.** Дешевле всего и честно при явной оговорке в профиле |
| **(в) Правка системной зоны 2348** | Патч `monread%`/рантайма: на EOF писать статус в зарезервированную ячейку вместо `STOP*`; обучить `IOEND*`/`READ*` её читать | Реверс скомпилированного рантайма + пересборка диска + регрессия золотых бинарников; **десятки чел.-дн.** (согласно `17-lun-p7c.md §7`) | **Истинная** F77-семантика `END=`/`ERR=`/`IOSTAT=` | Единственный путь к настоящему статусу. **Не в этой волне**; вне владения; erfordert отдельный проект `P7c/monitor` |

**Почему не (а) для J4/J23 прямо сейчас:** даже если обёртка вернёт `reg[016]`, стандартный
`READ` всё равно вызовет `monread%`, который на следующей карте снова уйдёт в `STOP*`.
Чтобы обёртка работала, надо либо полностью заменить ею formatted READ (нереально в 1 зоне),
либо всё же патчить рантайм — то есть вернуться к (в).

## 3. Выбранное соглашение и точная спецификация lowering (задание 3)

### 3.1 Соглашение профиля (фиксируется в F77 conformance profile on FOREX 5.00)

1. **Рабочий канал ввода — безъюнитный `READ` из(card-queue stdin).** Юниты 1/2/5/6/10/40/45
   в F77-слое не работают (`15-io.md §5.1`); поэтому `READ(u,fmt,…)` lowering-ится в
   безъюнитный `READ fmt,…` (юнит отбрасывается). Это та же база, что правила R10/R11
   из `15-io.md §4.3`.
2. **EOF и ошибка кодируются значением первой переменной списка:**
   - `-999999.` — EOF (метка `END=`);
   - `-888888.` — ошибка (метка `ERR=`).
3. **`IOSTAT=` эмулируется целочисленным кодом** в типизированном INTEGER-объекте:
   `0` — успех, `-1` — EOF, `+1` — ошибка. (X3.9: отрицательное значение = EOF;
    конкретные magnitudes — implementation-defined, что допустимо для профиля.)
4. **Всё это — эмуляция по значению, а не аппаратный IOSTAT.** Host обязан подложить
   карту-ловушку; реальные аппаратные ошибки не перехватываются (рантайм завершает задачу).
5. **Проверяется только первая переменная** (`v1`) — оговорка профиля, не полная семантика X3.9.

### 3.2 Спецификация для владельца `prep_tools.py` (правила R11-END / R11-ERR / R11-IOSTAT)

**Вход:** `READ(u,fmt [,END=Lend] [,ERR=Lerr] [,IOSTAT=k]) v1,…,vn`
(эквивалент нативной формы, которая транслятором 2.02 отвергается).

**Выход (порядок излучения строк строго фиксирован):**

```
[1]  k = 0                              ; ТОЛЬКО если есть IOSTAT=  (инициализация успеха)
[2]  READ <fmt>,v1,…,vn                  ; юнит u ОТБРАСЫВАЕТСЯ; fmt — динамическая метка
[3]  IF (v1 .EQ. -999999.) k = -1        ; ТОЛЬКО если есть IOSTAT=
[4]  IF (v1 .EQ. -888888.) k = 1         ; ТОЛЬКО если есть IOSTAT=
[5]  IF (v1 .EQ. -999999.) GO TO Lend    ; ТОЛЬКО если есть END=
[6]  IF (v1 .EQ. -888888.) GO TO Lerr    ; ТОЛЬКО если есть ERR=
```

Примечания к спецификации:
- Если `END=` и `IOSTAT=` заданы **вместе**, допустимы оба варианта; профиль выбирает:
  **сначала выставить `k=-1` (строки 1/3), затем перейти на `Lend` (строка 5)**. Это
  отличается от X3.9 (там при `IOSTAT=` ветка `END=` не берётся), но является объявленной
  оговоркой профиля — зафиксировать её в docs явно.
- Для INTEGER `v1` константы пишутся без точки: `-999999`, `-888888`. Для REAL — с точкой.
  Для COMPLEX/double/CHARACTER значение сентинала задаётся отдельной оговоркой (COMPLEX
  `.EQ.` в ФОРЭКС 2.02 может не поддерживаться — помечать как PARTIAL).
- Для `READ(*,*,END=…)` (list-directed) вместо `<fmt>` подставляется сгенерированная
  метка `9500+seq` и FORMAT по типам списка ( правило R10, `15-io.md §4.2`), БЕЗ `1X`.

**Обязательства HOST (без них lowering не исполняемо):**

| # | Обязательство |
|---|---|
| H1 | Для каждого lowering-нутого READ дописать сентинал-карту **сразу после его настоящих данных**. Если в одном READ есть и `END=`, и `ERR=`, дописать **две** карты: сначала `-999999.`, затем `-888888.` (порядок проверок в [3]-[6] именно этот). |
| H2 | Значение сентинала не должно коллидировать с данными. Выбирать вне диапазона задачи; факт выбора фиксировать в options/gold. |
| H3 | FORMAT для READ — **без `1X`** (иначе теряется первый символ числа). Ширина ≥ 9 для `-999999.` (проверено на `F12.4`). |
| H4 | **Циклы:** сентинная карта читается на первой же итерации. Для `DO I=1,N` с N READ-ами host обязан знать N и разместить сентинную карту **только после последней** реальной карты, а проверку [5]/[6] — после цикла (или развернуть цикл). Прямое «append per READ» корректно только для линейного кода. |
| H5 | Сентинал `-888888.` («ERR=») достижим **только по инициативе host**. Настоящая аппаратная ошибка ввода не превращается в эту ветку. |

**Честность.** Это emulation по значению; документ профиля обязан содержать оговорку:
«END=/ERR=/IOSTAT= реализованы в FOREX 5.00 через карты-ловушки и сравнение первой
переменной; настоящий статус ввода требует правки системной зоны 2348 (P7c/monitor)».
Статус элементов J7/J8 остаётся **OK\*** (lowering с оговоркой), IOSTAT — **новый OK\***
лишь после принятия этого правила владельцем `prep_tools.py`.

## 5. Что осталось блокирующим

1. **Истинный EOF/IOSTAT в рантайме (главный блокер).** Патч зоны 2348: на `reg[016]==0`
   в `monread%` вместо `STOP*` — запись статуса в зарезервированную ячейку + обучение
   `IOEND*`/`READ*` её читать и генерировать ветку/IOSTAT. Без этого `END=`/`ERR=`/`IOSTAT=`
   остаются OK\* (эмуляция), а не нативная семантика X3.9. Оценка: 5–10 чел.-дн.
   (`17-lun-p7c.md §7`), плюс регрессия золотых бинарников.
2. **J4/J23: каналы юнитов.** Даже с EOF-сигналом `READ(u,fmt)`/`READ(u)` не работают,
   пока не патчена LUN-таблица уровня B и не активирован канал (см. `17-lun-p7c.md §3`).
   EOF — необходимое, но недостаточное условие.
3. **Владение правилом.** Спецификация §3 отдана владельцу `prep_tools.py`; пока rule
   R11 в нём не обновлён, J7/J8 остаются на текущих sentinel-деках, а IOSTAT не lowering-ится
   совсем (`11-p7-alternatives.md:85`).
4. **Оговорки профиля H1–H5** должны быть внесены в документацию профиля, иначе deck/gold
   с сентиналами будут lexical-несовместимы с реальными данными (коллизия `-999999.`).

**Рекомендация родителю:** принять (б) как рабочее соглашение профиля и передать §3 владельцу
`prep_tools.py`; завести отдельную задачу `P7c/monitor` на (в) — единственный путь к честному
нативному IOSTAT; статус J7/J8 оставить OK\*, J4/J23 — PARTIAL/NO до патча LUN.
