## 1. Почему дамп был 196608 байт (задача 1)

`cu.c:284-303` — ветка `BESM6_CORE_ON_PC`. Цикл дампа (`cu.c:293`) пишет 65536 слов ×
6 байт = **393216 байт**, комментарий обещает «полное ядро (супервизор 0100000+)».

Размер `core[]` **не** является ограничением:

```
defs.h:51  #define CLICKSZ 1024
defs.h:52  #define NCLICKS 32
defs.h:53  #define CORESZ  (NCLICKS * CLICKSZ)   /* 32768 */
defs.h:204 EXTERN word_t core[CORESZ * 2];      /* 65536 слов — ВСЯ память */
```

То есть `core[] = 65536` слов, и цикл 0..65535 полностью его покрывает.

**Причина 196608 (32768 слов) в волне 18:** бинарник
`/home/azizz/Yandex.Disk/dispak/build/dispak/dispak`, которым снимался дамп, был
собран **до** коммита `4bbc051` (13.11, «дамп полного ядра 65536 слов»). `git blame`
`cu.c:293` подтверждает: раньше цикл был `q < 32768`, 13.11 заменён на `q < 65536`.
Это **устаревший бинарник**, а не урезанная сборка — исходник уже содержит исправление.

Проверка: свежая сборка из копии исходника даёт ровно `393216` байт
(`/var/tmp/p7c-core/dumps/core_full.bin`, `core_err.bin`, `core_check.bin`).

## 3. Где формируется сообщение (задача 3)

Дек `base_u45.b6` (`WRITE(45,10) 45`) воспроизводит `НЕТ КАНАЛА  LUN 45`, rc=0.

**Точные PC (из P7C-трассы, номера строк в `runs/tracefull/err.txt`):**

| Событие | PC | Строка | Команда |
|---|---|---|---|
| Program U45 | `001000` | 220292 | `xta 16` … `uj 01021` |
| WRITE-routines, *70/*75 | `000437`/`000451` | 220360 | `Э70`, `Э75` |
| Чтение ячейки LUN-проверки | `002004R` | 267586 | `xta 02251` |
| Установка кода ошибки | `001373R` | 2010414 | `vtm 02474, r7` |
| **Вызов ERRLUN** | `003233L` | 2010811 | `uj 04305` |
| **Тело ERRLUN** | `004305` | 2010812 | `vtm 04225,r10; ntr 3` → печать |
| **Печать строки** | `003326R` | 2012168 | `*64 a=2` (extracode e64) |
| STOP | `000411` | 2012243 | `*74` |

Маркер вывода `P7C-OUT #44` содержит GOST-байты
`055 045 062 / 052 040 055 040 053 040 / 104 111 105 / 004 005` =
«НЕТ КАНАЛА  LUN 45». Сообщение **не** является непрерывной константой ни в дампе,
ни на диске во всех перебранных кодировках (GOST, GOST+1/e64, ISO-8859-5, TEXT6,
ITM) — оно собирается посимвольно.

**Источник текста (READ-ONLY, найден):**
`monitor80-re/permanent/erriom.asm`:
```
TНETКAН : , ISO ,12H HET KAHAЛA      ; "НЕТ КАНАЛА"
TLUN    : , ISO ,6H’’ LUN            ; "  LUN"
ERRLUN  : , ENTRY                     ; VTM TНETКAН → SDEC → вых*ERRIOM
```
Перевод ISO→GOST на лету делает `ISOTEX` (вызывается из `GIVEMT` и др.), поэтому
GOST-байтов в памяти/на диске нет. Символ `ERRLUN = 04305` из дамба символов —
**реальный код**, в отличие от вывода волны 18 (`04305` там же называется TEXT-
литералом «МОНИТОР»; в этой волне PC 004305 реально исполняется, строка 2010812).

## 4. Таблица допустимости LUN (задача 3, continued)

В памяти (дамп на момент ERRLUN) обнаружена таблица по адресам **`0o02200..0o02273`**
— по одному 48-битному слову на LUN 4..63. Формат слова:
`[A=24 бита] [B=24 бита]`, где `A = LUN + 0100` (восьм.), `B = [флаги][LUN]`.

LUN 45 → память **`0o02251`**, значение **`0o15503200055`** (`00006d0d002d`).
Соседи: LUN 44 = `0o15400000054` (флагов нет), LUN 46 = `0o15600000056`.

Три копии этой таблицы найдены на **обоих** системных дисках (2348 и 2048) в
физических зонах 142(0o216)/263(0o407)/278(0o426), слова 5/0o332/0o1532
(логические зоны 0o212/0o403/0o422), 8-байтовые uint64 words, данные — младшие
48 бит (little-endian).

Проверка `BESM6_WATCH=02251` показала, что ячейка — **рабочая**, а не статичная:
в неё пишут `03765R` (загрузка), `00703L`, `03546L`, `64077L` и др.; на момент
проверки `002004R` она равна 0, а к моменту ERRLUN — уже значению таблицы.

## 5. Патч и прогон (задача 4)

`patch.json` (сохранён в `/var/tmp/p7c-core/patch.json`):

```json
[
 {"zone":"0o212","word":"0o5","old":"0o15503200055","new":"0o15500000055"},
 {"zone":"0o403","word":"0o332","old":"0o15503200055","new":"0o15500000055"},
 {"zone":"0o422","word":"0o1532","old":"0o15503200055","new":"0o15500000055"}
]
```

Применялось через `tools/patch_system_disk.py apply … --fix-checksum`
(только к копиям в `/var/tmp/p7c-core/exp/`), эталон не трогался. Перепробованы
значения `new`: `0o15500000055` (сброшены флаги), `0o15540000055` (как LUN 40),
`0o15513000055` (как LUN 41), `0o15500001055` (как LUN 48/54),
`0o15503200053` (как LUN 43). Патчились все 3 копии в 2348; отдельно — все 3 копии
в 2048 (именно они реально меняют память `0o2251`).

**Результат:** во всех случаях `WRITE(45,10)` по-прежнему печатает
`НЕТ КАНАЛА  LUN 45`; число 45 не появляется.

**Контрольный эксперимент (poke):** принудительная запись в память `0o2251 =
0o15500000055` directly в момент `PC=002004` (`BESM6_P7C_POKE`) **убирает**
`НЕТ КАНАЛА`, но вместо 45 появляется `БЫЛИ ОШИБКИ В СМ/СОSУ МАССИВАХ`.
То есть слово `0o2251` действительно управляет переходом в ERRLUN, но одной
правки таблицы недостаточно: на момент проверки ячейка обнуляется кодом
инициализации, а сама операция записи на LUN 45 не имеет рабочего канала/файла
(level A `disks[]` / PERSO). Для LUN 54 (эталон `write_u54`) WRITE печатает 12345 —
это встроенный печатающий юнит, а не дисковый.
