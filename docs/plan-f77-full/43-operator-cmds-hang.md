# 43 — P7c / ЗАДАЧА 4: зависание и операторские команды

## VERDICT

**КОМАНДЫ НЕ ВИНОВАТЫ.** Зависание наступает **после** успешного приёма колоды
(`B075-1 410300000000`), до того как раннер успевает подать `ВЦП`/`НОМ`/`ВЫБ`.
На изолированных копиях тот же самый «завис» воспроизводится **вообще без
операторских команд**: достаточно `Ctrl+G → at vu0 … → d 6 1 → d 5 10 → set cpu req → go`.
Одиночные команды, включая заведомо неправильную `НШИФ`, не останавливают ОС:
она отвечает `ОШИБ` и продолжает работать. `go` после `set cpu req` не вызывает
зависания: FS8-прерывание отработано (колода принята, задача `ЧП(075)` зарегистрирована),
а сэмплирование СчАС показывает, что процессор **выполняет код задачи**, а не стоит
в петле обработки прерывания или в цикле опроса терминала.

## 3. Гипотеза `pipe-buffer` — опровергнута как причина

`tmux pipe-buffer` **не существует** в этой сборке:

```
$ tmux list-commands | grep pipe
capture-pane …  pipe-pane …  paste-buffer …  # pipe-buffer отсутствует
$ printf 'НОМ\r' | tmux pipe-buffer -t s -
unknown command: pipe-buffer        # rc=1
```

Поэтому `send()` в `tools/run_besm6_deck.py:73-88` **всегда** идёт по ветке
fallback (`tmux send-keys`, строки 84-87). Никаких байтов через `pipe-buffer`
в панель не попадает, значит «хвост символов в буфере ввода от pipe-buffer»
физически невозможен.

Выедшиеся в живую панель `0` последовательности `^[[A^[[B^[[D^[[C`
(вместе с `sim> set`) — это escape-коды стрелок `send-keys Up/Down/Left/Right`,
а не остаток кириллицы из `pipe-buffer`. Они висят приглашении `sim>`, а не в
очереди ввода ОС, и на команды не влияют.

Проверка «бесконечного потока»: после `B075-1` посланные `НОМ`/`ВЦП` **эхо-
ируются** в панели, но не обрабатываются. Это признак занятого CPU задачей, а
не переполненного ввода: при переполнении ОС выдавала бы `НШИФ`/`ОШИБ`
(как в `ВВОД_АНАЛИЗ.md:221-223,315`). Повторный `go` не «прочищает» ввод, но
позволяет снять дамп СчАС.

## 4. Что происходит после `B075-1`

`B075-1 410300000000` — подтверждение приёма колоды (задача `ЧП(075)`, `M=005`).
Следовательно FS8-прерывание **обработано**, `set cpu req` сработал, `go` запустил CPU.
«Завис» — это долгая работа самой задачи (FOREX-трансляция / runtime), а не простой
операторской команды.

Сэмплирование СчАС (`f77_28_cmds_pc_sample.txt`, Ctrl+G → `go` каждые 4 c):

| t | СчАС | Контекст |
|---|---|---|
| +5 c | 21211 | `сч 73362, -> и 152(10)` |
| +9 c | 75361 | `-> или 151, или 152` |
| +14 c | 74131 | `-> или 73411(16), пе 77632` |
| +19 c | 66643 | `-> зп 72266(2), цикл 66642(2)` |
| +24 c | 66643 | тот же участок |
| +29 c | 74776 | `сбр 163, -> цикл 74776(2)` |

СчАС меняется — процессор активно исполняет код, включая печать (`пе 77632`)
и циклы FOREX. R-state живого PID 1523202 — нормальный признак работающего
эмулятора, а не замороженного. Задержка 6 ч объясняется `runlimit 200M
instructions` в `run.ini` batch-прогона, а не очередью команд.

## 5. Сравнение с `UVU/expect.ini` и `README/COMMANDS.md`

- `simh/BESM6/UVU/expect.ini:10-14`: `d 6 1 / d 5 10 / set cpu req / expect -r "Л[01].*\n" / go`.
  Там CPU уже запущен (`do dispak.ini` в строке 6), поэтому `expect` имеет смысл.
  Наш раннер останавливает CPU (`Ctrl+G`, `run_besm6_deck.py:212`) и потому не может
  дождаться `В0`/`Л0` до `go` — но, как показано выше, это различие не определяет завис.
- `UVU/expect.ini:22-27`: принтер включается **после** приёма задачи фронтальной
  панелью (`d 6 10 / d 5 1 / set cpu req / expect "ECT" / go`). Наш раннер делает
  `ДАЙ А0`/`ДАЙ А1` **до** колоды (`run_besm6_deck.py:202-205`) — даже это не меняет
  исход (см. таблицу 2.2).
- `UVU/expect.ini:17,30`: латинская транслитерация `WCPP`/`HOMB` — это особенность
  сценария, а не требование ОС. Наша кириллица распознаётся корректно.
- `simh/BESM6/README/COMMANDS.md` — справочник **команд агента** (ПРОКОММЕНТИРУЙ,
  ОТЛАДИТЬ ЭМУ и т.п.), к операторским директивам ДИСПАК отношения не имеет;
 Полезный материал по operator-level командам — `re-dispak/docs/COMMANDS.md` и
  `simh/BESM6/docs/ВВОД_АНАЛИЗ.md:§3.2,3.4,3.4а`.

## 6. Минимальное исправление раннера

**Для устранения зависания исправление не требуется** — причина не в командах.
Ниже — только устранение *латентных* дефектов самого раннера (не влияют на завис,
но делают поведение честным).

1. `tools/run_besm6_deck.py:73-88` — `pipe-buffer` не существует; убрать
   иллюзию и явно использовать `send-keys`:

```python
def send(session, text, enter=True):
    # tmux 3.7b: pipe-buffer отсутствует; send-keys с unicode-консолью
    # (OSZAGR/dispak.ini:138) корректно передаёт кириллицу.
    tmux("send-keys", "-t", session, text)
    if enter:
        tmux("send-keys", "-t", session, "Enter")
```

2. `tools/run_besm6_deck.py:212-217` — дождаться приглашения `sim>` после `Ctrl+G`,
  иначе SIMH-команды уйдут в консоль ОС и дадут `НШИФ`/`ОШИБ`
   (`ВВОД_АНАЛИЗ.md:218-223`; подтверждено экспериментом `pc_sample.py` до правки):

```python
tmux("send-keys", "-t", args.session, "C-g")
wait_for(args.session, re.compile(r"sim>\s*$"), 10, "приглашение sim>")
for cmd in (attach, "d 6 1", "d 5 10", "set cpu req", "go"):
    send(args.session, cmd)
    time.sleep(0.5)
```

3. `tools/run_besm6_deck.py:219-228` — не интерпретировать тишину после `B075-1`
   как «завис команд»: увеличить `--timeout` и отслеживать СчАС/АЦПУ. Команду `ВЦП`
   (`run_besm6_deck.py:237`) имеет смысл подавать только когда `DONE_RE` не сработал
   и CPU действительно в `idle` (приглашение `sim>`, `СчАС 04440`).
