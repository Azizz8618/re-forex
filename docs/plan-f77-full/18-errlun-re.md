## 2. Ключевая корекция предыдущей волны (главный результат)

В документе 17 (`§1.2`, `f77_17_lun_table.txt:29-30`) утверждалось:
«ERRLUN виден в дамбе символов на адресах 04305/04317/04321; попытка
`BESM6_CORE_ON_PC=04305` не сработала, потому что ERRLUN вызывается не напрямую».

**Это объяснение неверно.** Дизассемблирование `core65007.bin` по 04200–04300
показывает:

```
04300  Э70 48 ; 04301 Э70 40 ; 04302 Э70 111 ; 04303 Э70 112 ; 04304 пб 62
04305  конд в'5557565164576212'   <- НЕ команда, а TEXT-литерал
```

Адреса 04305/04317/04321 — это **строки имени в таблице символов
компоновщика/компилятора**, значения символа, а не код процедуры `ERRLUN`.
Слово 04305 по TEXT6 (`text_to_gost`, `encoding.c:377-411`) читается как
`М О Н И Т О Р` + паддинг; тот же литерал повторяется на 04262 и 00405.
Следовательно ловить PC дампом по 04305/04317/04321 было бессмысленно —
нужны адреса **кода**, которые из символьного дампа не следуют.

## 3. Где (скорее всего) живёт проверка — что удалось сузить

- Сообщение **не** является непрерывной константой ни в системной зоне
  диска 2348, ни в загруженном ядре (0..077777). Значит оно либо
  собирается посимвольно print-рутиной МОНИТОР-80, либо resides в
  супервизоре 0100000+, который текущая сборка эмулятора в `core-pc.bin`

- Э50 0131 (attach) остаётся без эффекта — подтверждено в 17-й волне;

### 8.2 Найденный PC печати

Строка 2012528 полного трейса:
```
MTR 02506R *67    20(14) AU=1503244010020040
   M: ... 14=02505 15=04252 ... R17=75401
```
**PC = `02506R`**, экстракод `*67`, адрес `0020`, индекс `M14=02505`.
В трейсе ровно 5 `*67`; остальные — ранняя печать (00076, 03200, 01777,
02012); пятый (02506R) — искомый.

Цепочка (строки 2011278..2012550):
```
03303/03304 -> 04476 (vzm 4501(1), 5 проходов)
   -> 04501..04525 (упаковка символов, M3=04253..04255 = указатель буфера)
   -> 04525R uj 0(15) [R15=04304]
   -> 04304L uj 4251(0) -> 04251L vjm 2505(15)
   -> 02505 wtc 432 / 02506R *67 20(14)   <- ПЕЧАТЬ
   -> 02522R uj 0(15) -> 00411L *74 STOP
```
Последние E70/E50: `E70at 00051L uil=70/45`, `DD pc=00052 u=20 z=0004 RD`,
R16=00045 (Fortran-юнит) — сохраняется на всём пути к отказу.

### 8.3 Дамп ядра и оверлейный сюрприз

`BESM6_CORE_ON_PC=02506 BESM6_CORE_SKIP=4` → `core2506.bin` (196608 байт,
32768 слов). В этом дампе слова **04304/04305 содержат КОМАНДЫ**
(`4011032000360107` / `5013000040130327`), тогда как в дампе на PC=65007
те же адреса были TEXT-литералом «МОНИТОР». ⇒ область 043xx — **оверлей**,
перезагружаемый по ходу задачи. Значит даже найденный «адрес ERRLUN» из
символьного дампа не является стабильной целью патча.

### 8.4 Почему patch.json НЕ составлен (честно)

Константа сообщения отсутствует во ВСЕХ обследованных носителях и кодировках:
диски 2048/2348, PERSO `FOREX_PERSO_2300.bin`, три `core-pc.bin`;
GOST-10859, TEXT6, ITM, KOI8-R, CP1251, CP866, ISO-8859-5, ASCII;
упаковки 6×8 и 7×6 на слово, все границы. Сообщение собирается динамически
в оверлее. Статической зоны.слова с битом «разрешён для 54 / запрещён для 45»
в образе 2348 не существует — её нельзя выписать и нельзя пропатчить
`tools/patch_system_disk.py`. Патч = выдумка, поэтому не делается.
