# 61. Находки: программа выбора транслятора в Мониторе-80 (22.11.2026)

Сводка всех находок по вопросу «как Монитор-80 определяет вызов нового
транслятора и где он лежит». Исправляет более ранние ошибочные выводы F1
(см. `logs/f77_30_60_f1_monitor80_search.txt` с исправлением в конце).

## 1. МАДЛЕН-исходник ЕСТЬ (нашёл главный агент)

Программа называется не `NEWCOMP*`, а **`GIVTRAN*` / `SETTRAN*` / `TTABLE*`**:

- `monitor80-re/permanent/givtran%.asm` (43 строки) — полный МАДЛЕН-исходник:
  - `GIVTRAN*: , NAME,` — "Монитор-80" ИАЭ;
  - `TTABLE* : , SUBP,` — таблица трансляторов;
  - `SETTRAN*: , ENTRY,` — точка входа (вызывается из `star%.masm:118`:
    `M13, VJM, SETTRAN*`);
  - логика: `XTA MONCARD*` (карта `*TRANS`) → `M14, VTM, TTABLE*` (чтение
    таблицы) → `AEX для*тип*трн` (сравнение) → `UZA в*STACOMP` →
    `UJ STACOMP*`.
- `monitor80-re/permanent/ltable%.asm:37-38`:
  ```
  , ISO ,6Н*TRANS
  , TEXT,8НNEWCOMP*  .+
  ```
  это продолжение таблицы `TTABLE*`: `*TRANS` maiden'ится в `NEWCOMP*`.
- `monitor80-re/permanent/star%.masm` (STAR*, «новые транслиторы»):
  `SETTRAN*: , SUBP,` (строка 32), `TRCAT*: , LC ,17` (каталог трансляторов).

**Вывод:** F1 ошибался, ища файл по имени `NEWCOMP*`; исходник — `givtran%.asm`.

## 2. Скомпилированный бинарник на диске

- диск `/usr/local/share/besm6/2048`, **зона `0o422`**, слова `0o777..`;
- файловые смещения `0x2315b8..` (формат: 1032×uint64 LE, зона+4, заголовок 64 байт);
- первые 7 слов совпадают с RAM `0o3000..0o3006` байт-в-байт;
  (`0042001500030017 0036011200360066 0040001356502000 ...`);
- остальные слова при загрузке трансформируются (полного 64-словного
  непрерывного совпадения нет);
- дизассемблинг `reference/m80/NEWCOMP_zone422.dis` (disbesm6; слова `0o770..0o1007`
  — данные/TEXT, код от `0o1010`); сырая зона `reference/m80/zone422.bin`.

## 3. Элемент, формирующий VJM-слово (E1)

- источник: RAM `0o36621` ← диск 2048, логич. зона `0o227`, слово `0o621`;
- в файле (8-байтовые uint64 LE) смещение `0x139388`, байты `00 00 09 02 80 dc`;
- рантайм-цикл `0o64415..0o64427` собирает из него слово по RAM `0o455`:
  `6710000202200000` = `vjm 64002(15)`;
- two-byte patch `0x13938b/0x13938c: 02 80 → f8 9b` даёт
  `6711577002200000` = `vjm 1770(15)` на непатченном dispak (E1,
  `logs/f77_30_59_e1_binary_patch.txt`);
- блокер: RAM `0o1770` пуст в момент первого VJM; trampoline в зоне `0o201`
  дал `КОНТРОЛЬ КОМАНДЫ`, пробовать зону `0o207`.

## 4. Быстрая правка таблицы TTABLE на диске (рекомендация пользователя)

Пользователь указал: **патчить таблицу `TTABLE` прямо на диске — как вариант
быстрой правки**. Это проще, чем патч кода/монитора:

- `TTABLE*` читается `SETTRAN*` (`M14, VTM, TTABLE*` в `givtran%.asm`), её
  отображение `ltable%.asm` задаёт `*TRANS → NEWCOMP*`;
- нужно найти физические слова таблицы на диске 2048 (зоны каталога
  трансляторов) и заменить имя `NEWCOMP*` на имя нашего модуля — тогда
  `*TRANS:...` выберет его без правки кода загрузчика;
- точные смещения TTABLE на диске ещё не определены — следующий шаг.

## 5. Ограничение на правки (пользователь)

`docs/corrections.md` (коммит `ce7fab3`): **dispak править только если в нём
не реализована функция/экстракод**; во всех остальных случаях — задача
пользователя, включая монитор‑80. Поэтому C3-патч `cu.c`/`defs.h` — только
доказательство механизма, не целевое решение; целевое — бинарный патч
монитора/таблиц на диске.

## 6. Смещения таблиц на диске 2048 (найдены, 22.11.2026)

Формат: 1032×uint64 LE на зону, логическая зона L → физическая L+4,
заголовок 64 байта, смещение слова w = (L+4)*8256 + 64 + w*8.

**TTABLE (`ttable%.asm`, ISO→TEXT):** зона `0o240`, слова `0o403..0o434`
(дубли: зона `0o243` слова `0o1444..0o1474`, зона `0o250`):
```
0o240.0404 ASEMBLER   0o240.0406 FORTR*    0o240.0410 INITFTN
0o240.0412 ALGOL*     0o240.0414 BEMSH*    0o240.0416 REFAL*
0o240.0420 PASCAL*    0o240.0422 FOREX*    0o240.0424 SIMUL*
0o240.0426 SIM67*     0o240.0430 *PASCOM   0o240.0432 PGN*
0o240.0434 FOREX3*    0o240.0436 'TTABLE*' (имя таблицы)
```
Пара `*FORX3 → FOREX3*`: ISO-слово `0o240.0433` (`*D9/4EЗS`), TEXT-слово
`0o240.0434` = `4657624570231200`.
File offset `FOREX3*` в зоне 240: `0x14b220`.

**STABLE / LTABLE (`ltable%.asm`, для дизассемблера):** зона `0o230`,
слова `0o770..0o777`; `*TRANS → NEWCOMP*` — пара `0o230.0774/0775`,
TEXT-слово `NEWCOMP*` = `5645674357556012`, file offset `0x13b728`.

**Проверено на копиях (stock dispak):**
- патч `0o230.0775` NEWCOMP*→FOREX*: на `*TRANS` и `*TRANS:FOREX3*,,411550`
  поведения не изменил (обе версии дают ФОРТРАН /16.07.73 / 4.12);
- патч `0o240.0434` FOREX3*→OURMRK* и дубля `0o243.1474`: на
  `*TRANS:FOREX3*,,411550` поведения не изменил; на `*TRANS:*FORX3,,411550`
  обе версии (patched/baseline) дают только `КОНЕЦ ЗАДАЧИ`.

**Вывод:** адреса таблиц установлены точно, но быстрая правка их не даёт
управления выбором компилятора в проверенных сценариях: при явном имени
(`*TRANS:FOREX3*`) NEWCOMP* ищет имя в каталоге на диске 41 (зона 1550), а
при `*TRANS` без имени используется маршрут по умолчанию. Для надёжной
быстрой правки нужно патчить **каталог зоны 1550 диска 2148** (там имя
`FOREX3*` в паре с дескриптором) — это проверенный в M3/M4 путь.

## 7. РЕШАЮЩАЯ НАХОДКА: LINK-таблица монитора (бинарник + МАДЛЕН)

Корреляция бинарника и текстов (22.11.2026) дала точный механизм.

**МАДЛЕН-тексты:**
- `givtran%.asm` — скомпилирован в DMS-модуль, имя `GIVTRAN*`; entry `SETTRAN*`;
  SUBP `TTABLE*`; external `STACOMP*`, `NEWCOMP*`; entry-код:
  `XTA MONCARD* → чт*тбл*трн → VTM TTABLE* → AEX для*тип*трн → UZA в*STACOMP`.
- `ttable%.asm` — ISO→TEXT таблица трансляторов (`*FORX3 → FOREX3*` и др.).
- `ltable%.asm` (STABLE*) — `*TRANS → NEWCOMP*` (для дизассемблера).
- `star%.masm` (STAR*) — вызов `M13, VJM, SETTRAN*`, каталог `TRCAT*`.

**Бинарник на диске 2048:**
- зона `0o200` — **LINK-таблица монитора**: пары TEXT-имя / адресное слово:
  - `200.0040` `GIVTRAN*` + `200.0041` адрес;
  - `200.0042` `SETTRAN*` + `200.0043` = `1`;
  - `200.0044` `TTABLE*` + `200.0045` адрес;
  - `200.0330` **`NEWCOMP*`** (file offset `0x10a800`,
    слово `5645674357556012`) + `200.0331` адресное слово `6510700004300000`
    (SHX 0o430(M14)).
- зона `0o422` — скомпилированный код `NEWCOMP*` (RAM `0o3000..`);
- зона `0o240` — TTABLE (ISO/TEXT пары), зона `0o230` — STABLE.

**ЭКСПЕРИМЕНТ (stock dispak, копия 2048):**
патч LINK-имени `200.0330` `NEWCOMP* → FOREX3*` привёл к появлению
**`ОТСУТСТВУЕТ NEWCOMP*`** (в baseline этой ошибки нет) — это прямое
доказательство, что `*TRANS` резолвится через LINK-таблицу зоны 200,
и именно её нужно патчить для быстрой правки.

**Быстрая правка (итог):** patчить LINK-запись зоны 200 — либо имя
`200.0330` (при этом монитор ищет новое имя), либо адресное слово `200.0331`.
Patch TTABLE/STABLE (зоны 240/230) на поведение не влияет.

## 8. ВЫПОЛНЕНИЕ «быстрой правки» LINK-записи (22.11.2026) — результат

Выполнены три варианта патча LINK-записи зоны 200 на копии 2048 (stock dispak):

1. **Имя** `200.0330` (offset `0x10a800`) `NEWCOMP* → FOREX3*` + карта `*TRANS`
   (без имени) → `ОТСУТСТВУЕТ NEWCOMP*`. Ментор ищет именно `NEWCOMP*` —
   патч имени ломает резолв (доказательство, что это резолвер).
2. **Адресное слово** `200.0331` (offset `0x10a808`)
   `6510700004300000 → 6610700010200000` (от STACOMP*) + `*TRANS` →
   тихий `КОНЕЦ ЗАДАЧИ`.
3. **Имя** `NEWCOMP* → FOREX3*` + карта `*TRANS:FOREX3*,,411550` →
   тихий `КОНЕЦ ЗАДАЧИ`.

**ВЫВОД:** LINK-запись зоны 200 действительно является резолвером `*TRANS`
(патч имени ломает поиск), НО простая подстановка имени/адреса не даёт
рабочего вызова транслятора: адресное слово — это `SHX 0o430(M14)`,
неразрывно связанное со структурой переходника (таблицы `0o430`), и требует
пересборки самой LINK-таблицы/переходника. «Быстрая правка» в sense
подмены одного слова **недостаточна** — нужен либо патч переходника
`0o430(M14)`, либо возврат к проверенному пути: подмена каталога на диске
2148 зона 1550 (M3 EXP B: `FOREX3*→OURCOM*` + `*TRANS:OURCOM*` работает).

## 10. МЕТОДИКА ВЫЗОВА КОМПИЛЯТОРОВ ПО ТЕКСТАМ МОНИТОРА-80 (22.11.2026)

Прочитаны целиком МАДЛЕН-тексты `monitor80-re/permanent/`:
`star%.masm`, `givtran%.asm`, `stacomp%.asm`, `ltable%.asm`, `ttable%.asm`, `execut.asm`.

**Полная цепочка вызова компилятора:**
1. `star%.masm:96-100` (`типработы`): `M13,VJM,GIVLIBR*` → `GIVSERV*` → **`GIVTRAN*`**
   — Define тип управляющей карты (`*FOREX`, `*TRANS`, `*FTN`, `*PASCA`...).
2. `star%.masm:116-118`: `XTA TRCAT*` (каталог трансляторов, `TRCAT*: LC 17`
   по `star%.masm:18` и `stacomp%.asm:9`) → `M13,VJM,SETTRAN*`.
3. `givtran%.asm`: `SETTRAN*` берёт `MONCARD*`, читает `TTABLE*`
   (`M14,VTM,TTABLE*`), сравнивает `AEX для*тип*трн`, при совпадении
   `UZA в*STACOMP` → `M14,XTA,1; UJ STACOMP*`.
4. `stacomp%.asm`: `STACOMP*` хранит имя в `TRNAME*`, ищет его в каталоге
   `TRCAT*` процедурой `dncomp`, грузит `STLOAD*`, делает `M15,*70,1`
   (чтение диска по экстракоду), проверяет `WRITLIB*`/`STPUNCH*`.
5. `execut.asm` (`*EXECUTE`): `LOADANGO` → передача управления загруженному
   компилятору.

**КЛЮЧ:** `TRCAT*` (17 слов) — каталог трансляторов, реально используемый
`SETTRAN*`/`STACOMP*`. `NEWCOMP*` в `ltable%.asm` — это маппинг **для
дизассемблера** (STABLE*), не рабочий каталог. Поэтому патч STABLE (зона 230)
и TTABLE (зона 240) не влияет на выбор: рабочий каталог — `TRCAT*`.

Адрес `TRCAT*` в LINK-таблице зоны 200: `TRCAT* @ 200.???` (найти точное слово
— следующий шаг); в `stacomp%.asm` он объявлен как `LC 17` (17 слов).

Следствие для быстрой правки: патчить нужно `TRCAT*` (каталог из 17 записей),
а не TTABLE/STABLE/LINK-имя.

**Дополнение к §10 — TRCAT* на диске:**
`TRCAT* (LC 17)` найден как 17-словный блок зоны `0o230.0747..0767` — пары
ISO/TEXT системных утилит (`COSTEP`, `EXITC`, `EXECUT`, `CATALOG*`, `OVERLAY*`,
`OCATALOG`, `RDMAC*`, `WRMAC*`, `TAPES*`...). Компиляторов в нём нет — это
каталог утилит STAR, а не трансляторов. Имена `INFLOAD*/STLOAD*/TRNAME*/TRCAT*/
STCAT*/ASTL*/LUN*MON` в зоне 230.0720..0726 — COMMON-блок `stacomp%.asm`,
не значения.

**Итог изучения текстов:** все три кандидата на «каталог» (TRCAT зоны 230,
TTABLE зоны 240, STABLE зоны 230.0775) при патче на диске не меняют выбор
компилятора по `*TRANS` в проверенных сценариях. Единственный рабочий
резолвер, доказанный EXPERIMENT — каталог зоны `0o1550` диска 2148 (§9).
Тексты дают схему вызова (GIVTRAN→SETTRAN→TTABLE→STACOMP→LOADANGO), но
физический выбор имени идёт через загрузочный каталог 1550.

## 11. ПОЧЕМУ ПАТЧИ TTABLE/STABLE/TRCAT НЕ РАБОТАЮТ — ПРИЧИНА (22.11.2026)

**Причина найдена:** `TTABLE*`, `TRCAT*`, `STABLE*` в МАДЛЕН — это **SUBP/ENTRY
модули и символические LINK-имья**, а не «текстовые таблицы на диске», которые
можно патчить по TEXT-слову.

Доказательства:
- `givtran%.asm:5` `TTABLE* : , SUBP,` — это подпрограмма; `M14,VTM,TTABLE*`
  (`givtran%.asm:20`) читает результат её работы, а не статический массив по
  TEXT-имени «TTABLE*».
- зона 200 диска 2048 — LINK-таблица монитора: пары «TEXT-имя → адресное слово».
  Там есть `GIVTRAN*(200.0040)`, `SETTRAN*(0042)`, `TTABLE*(0044)`,
  `STACOMP*(0324)`, `NEWCOMP*(0330)`, `LTABLE*(0152)`, `STABLE*(0154)`,
  но **нет** `INITFTN`/`FOREX*` — компиляторы не.resolвятся через неё.
- я пропатчил **все пять** копий `ASEMBLER→OURASM*` (зоны 240, 243, 250, 253,
  440) — `*FORTR` всё равно скомпилировал Fortran. Значит рабочие имена
  формируются в ОЗУ (процедурой TTABLE*/SETTRAN*), а не берутся из этих
  TEXT-слов на диске.
- `TRCAT*: LC 17` (star%.masm:18, stacomp%.asm:9) — это 17-словный COMMON-массив,
  создаваемый动态ически; копия в зоне 230.0747..0767 — каталог утилит STAR.

**Вывод:** для патча «методики вызова» по текстам нужно править **код процедур
GIVTRAN*/SETTRAN*/STACOMP* (скомпилированный в зоне 200+ и в LINK), либо
рабочие данные в ОЗУ**, а не TEXT-имя в зоне 240/230. Простая дисковая правка
 TEXT-имени не затрагивает execution path — поэтому Effect'а нет.

Единственный проверенный рабочий патч остаётся загрузочный каталог 2148 зоны
1550 (§9): он меняет имя, по которому NEWCOMP* ищет тело компилятора на диске.

## 12. КОНКРЕТНЫЕ МЕСТА КОМПИЛЯТОРОВ НА ДИСКЕ 2348 (22.11.2026)

Формат 2348: 1032×uint64 LE на зону, логическая = физическая (без +4),
заголовок 64 байта, смещение слова w = L*8256 + 64 + w*8.

**LINK-таблица монитора (зона 0o204, дубль зоны 200 на 2048):**
пары «TEXT-имя → адресное слово»:
```
204.0012 PRINT8//   204.0014 SHIFT*     204.0016 MTSHIFT*
204.0050 GIVTRAN*   204.0052 SETTRAN*   204.0054 TTABLE*
204.0330 NEWCOMP*   204.0332 STLOAD*    204.0334 BLEXPRIN
204.0336 *PASCAL    204.0344 IODCALL*   204.0346 LIBRARY*
```
Адресные слова (VJM-подобные): GIVTRAN `6451000001300000`,
TTABLE `6411000003300000`, STACOMP `6610700010200000`,
NEWCOMP `6510700004300000` — IR=6(MOD), KOP 41/45/61, ADR `10000`/`7000`.

**DMS-модули со ссылками GIVTRAN* (external):**
- зона `0o234.0301-0303`: `MONCARD* / GIVTRAN* / PRINT8` — LINK-таблица модуля,
  где GIVTRAN* — внешняя процедура;
- зоны `0o244.0465` и `0o247.1525`: `GIVTRAN*` в конце модуля — external LINK-имя.

**Все копии TTABLE/имён на 2348:** GIVTRAN* в зонах 204.50, 234.302, 241.667,
244.465, 247.1525, 1216.200, 1253.1170, 1711.1064; SETTRAN* в 204.52,
241.675, 1216.202, 1253.1172; TTABLE* в 204.54, 244.446/501, 247.1506/1541.

**Вывод:** конкретные места скомпилированных процедур GIVTRAN*/SETTRAN*/STACOMP*
на диске 2348 найдены (LINK-таблица зоны 204 + DMS-модули зон 234/244/247),
но они все — **LINK-имена/адресные слова**, патч которых (проверено на 2048,
§7-8) ломает резолв, а не подменяет логику. Рабочая логика выбора живёт в
загрузочном каталоге 2148 зоны 1550 (§9) — единственный проверенный патч.

## 13. ОБЪЕКТНЫЕ МОДУЛИ ПОДПРОГРАММ НА ДИСКАХ — ЧЕСТНЫЙ ИТОГ ПОИСКА (22.11.2026)

Искал DMS-объектные модули GIVTRAN*/SETTRAN*/STACOMP*/NEWCOMP* на дисках
2348 и 2048 по DMS-шапке (`head|sym<<12|debug<<36` с `head=0o1200 sym=0o7023`
как у FOREX3*). **Результат: таких DMS-шапок для этих имён НЕТ** — ни одного
совпадения с `0o4657000070231200` / `0o0000000070231200`.

**Что есть вместо этого:**
- все 18/26 вхождений GIVTRAN*/STACOMP* на 2348 — это LINK-имена в таблицах
  (зоны 200/204 — LINK монитора, 230/234 — COMMON, 240/244/247 — таблицы
  модулей, 1212/1216 и др. — копии);
- зона 240 (2048) / 234 (2348) — таблица модулей: слова 0..11 дескрипторы,

## 20. РАЗБОР КАТАЛОГА OVERLAY — ЧЕСТНЫЙ ИТОГ (22.11.2026)

`overlay.pl` выдаёт catalog-запись:
```
GIVTRAN* 60 0001 00 00166 01770
MONITOR* 20 0000 00 00000 00400
```
Предположение «60 0001 = volume 60, zone 1» проверено и **ОПРОВЕРГНУТО**:
запись пересобранного объекта в зону 1 диска 2048 И в зону 1 диска 2148
не меняет поведение `*TRANS` — печатается `REBUILT-M80-7391` из деки
(резидентный компилятор), а не наше `21 1.00 3.00`. `disas.pl -vol 2048
GIVTRAN` говорит `GIVTRAN IS ABSENT`.

Вывод: catalog `60 0001` — это НЕ прямая физическая зона диска 2048/2148,
а адрес внутри **оверлея/постоянной библиотеки**, который монитор грузит
в ОЗУ при старте (sv_load / Э70, зоны 0252+ и catalog OCATALOG). Для установки
пересобранного модуля нужно понять и воспроизвести формат OCATALOG/оверлея
(запись GIVTRAN* в зоне 0o240.0455 / 0o243.1515) — отдельная задача.

Патч dispak НЕ используется (откатен 8298e2c); тексты модифицируются и
пересобираются через asm.pl/overlay.pl (доказано в §17-19).
