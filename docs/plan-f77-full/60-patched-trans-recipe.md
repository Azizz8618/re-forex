# Рецепт 59-C3/60: пропатченный `*TRANS` и воспроизводимый тест

Статус: **DONE** (21.11.2026). Первичное доказательство:
`docs/plan-f77-full/logs/f77_30_59_c3_selfcontained.txt`.
Воспроизводимая форма: `tests/plan-f77/59-c3/run.sh` (этап D2).

Цель: зафиксировать, что через **пропатченный путь `*TRANS` монитора-80**
исполняются именно наши слова, без env-инъекции, и что это можно проверить
одной командой из репозитория.

## 1. Происхождение исходника и лицензия

- Канонический источник C-симулятора: репозиторий `dispak` (форк
  `https://github.com/besm6/dispak.git`), снимок сессии C3 с git HEAD
  `01d817b833bf906fd4be5dbc4c22f26a9b627b0f`.
- Лицензия: GNU GPL v2, текст сохранён в `tests/plan-f77/59-c3/src/COPYING`.
- В репозиторий положен **уже пропатченный** снимок исходников
  (`tests/plan-f77/59-c3/src/`) и эталонные diff
  (`tests/plan-f77/59-c3/patches/`). Diff-ы относились к промежуточному снимку C2
  (`/var/tmp/b1-f77-fix/59-c2/dispak-src`) и нужны для сверки, а не для
  наложения на исходное дерево: результат уже включён в `src/`.
- Факты ниже получены из исходников C3 и прогонов; выводы о том, что именно
  исполняется, подтверждены A/B и дампом ядра (см. §6).

## 2. Точные патчи

### 2.1. `dispak/defs.h`, макрос `STORE` (строки 284-289 снимка)

В момент записи монитором слова по RAM `0o455` подменяем его адресное поле.
Условие совпадает ровно с одним словом, собранным рантайм-циклом `0o64415..0o64427`:

```c
/* C1: redirect Monitor-80 VJM 64002(15) at RAM 0o455 to our body 0o1770 */
if ((addr) == 00455 && (reg).l == 0xdc8002 && (reg).r == 0x090000) {
        (reg).l = 0xdc9bf8;
        c3_install_our_words();
        fprintf(stderr, "C3PATCH pc=%05o 0o455: 6710000202200000 -> 6711577002200000\n", pc);
}
```

Преобразование слова (старшие 3 байта в `.l`, младшие 3 в `.r`):

| | 6 байт (hex) | 16-ричное слово |meaning |
|:--|:--|:--|:--|
| было | `dc 80 02 09 00 00` | `6710000202200000` | `vjm 64002(15)` |
| стало | `dc 9b f8 09 00 00` | `6711577002200000` | `vjm 1770(15)` |

Проверка адреса: `0o15770 + 0o64000 = 0o77770`, `0o77770 & 0o77777 = 0o1770`.
Патч стоит **до** декодирования в `STORE`, поэтому отдельного `NEXT;` (как в C2)
не требуется: когда PC станет `0o455`, CPU возьмёт уже патченное слово.
В начале файла (строки 38-40) добавлено объявление
`extern void c3_install_our_words(void);`.

### 2.2. `dispak/cu.c`, функция `c3_install_our_words()` (строки 19-56)

Блок C2 с `BESM6_REDIRECT_PC/TO/WORDS` ( diff `@@ -344,60 +380,6 @@` в
`patches/cu.c.patch`) удалён полностью. В точке того же `STORE`-хука вызывается:

```c
void
c3_install_our_words(void)
{
        static int done = 0;
        void *dh;
        char buf[ZONE_SIZE];
        int i, k;

        if (done) return;
        done = 1;
        dh = disk_open(2148, DISK_READ_ONLY);
        if (!dh) { fprintf(stderr, "C3: cannot open disk 2148 for body words\n"); return; }
        if (disk_readi(dh, 01745, buf, NULL, NULL, DISK_MODE_QUIET) != DISK_IO_OK) {
                fprintf(stderr, "C3: cannot read body zone 01745 from disk 2148\n");
                disk_close(dh); return;
        }
        disk_close(dh);
        for (i = 0; i < 11; ++i) {
                for (k = 0; k < 6; ++k)
                        core[01770 + i].w_b[k] = buf[(9 + i) * 6 + k];
                cflags[01770 + i] &= ~C_UNPACKED;
        }
        fprintf(stderr, "C3: loaded 11 body words from disk 2148 zone 01745 "
                        "into RAM 01770..01782\n");
}
```

`disk_readi(..., DISK_MODE_QUIET)` читает ту же физическую зону, куда харнесс
пишет телом через `besmtool write 2148 --start=01745` (в `disk_readi2` для
`DISK_MODE_QUIET` происходит `zone += ZONE_OFFSET(4)`). Слова **не захардкожены**:
при смене GOST-маркера в зоне `0o1745` меняются и байты в RAM, и печать (§6).
`disk.c` не менялся (дифф пустой).

## 5. Сборка и запуск

```sh

```

`src/` в рабочий каталог, `cmake -S src -B build -DCMAKE_BUILD_TYPE=Release`,

## 6. Что доказано и что нет

**Доказано FACTS:**

1. Патч `STORE` срабатывает один раз: в stderr ровно по одной строке `C3PATCH`
   и `C3: loaded 11 body words...`.
2. `vjm` по `0o455` подменён на `0o1770`; Execution идёт по нашему коду.
3. Слова приходят **с диска 2148, зоны 0o1745**, а не из константы и не из env:
   смена GOST-маркера только в `body` меняет печать на `BANNER-DISK-7391`
   (вариант `diskmarker`), при этом исходник патча не трогается.
4. A/B: обнуление `body[9]` убирает печать, восстановление возвращает. Значит
   печать выполняется именно нашим кодом, а не просто присутствует в RAM.
5. E64-трасса C3 показывает печать через наш дескриптор `0o1774`
   (`*** E64 01774-00000 ... FINAL=010`), в базовом прогоне адреса были
   `53450/53464/05307` (резидентные дескрипторы).
6. CORE DIFF (C3): RAM `0o1770..0o1782` совпадает с `body[9..19]` байт в байт;
   GOST-байты маркера в базовом дампе отсутствуют.
7. Системный диск не меняется (SHA256 до/после совпадает).

**НЕ доказано (границы):**

- Резидентный компилятор монитора-80 по-прежнему **загружается** в RAM, но в
  этом пути он **не вызывается**: переход по `0o455` идёт на наш код.
- Сам компилятор ещё **не выдаёт объектные данные**: тест печатает фиксированный
  маркер из подготовленного тела. Компиляция исходника и выдача объектного
  результата - задача **D1**, этот тест её не подменяет.
- Тест проверяет патч в C-исходнике симулятора, а не пропатченный загрузочный
  образ на физическом диске и не исправление самого монитора 4.12.
- Слова тела подготовлены харнессом из текстовых фикстур (это те же слова, что
  которые использовались в C3), а не заново скомпилированы нашим компилятором.
